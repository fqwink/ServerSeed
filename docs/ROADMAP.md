## Phase 2: 共通基盤と構成選択

- 対象: [共通基盤](BASIC_SPEC.md#共通基盤と状態管理)、[共通設定](BASIC_SPEC.md#共通設定とデータ形式)、[OS・アーキテクチャ判定](BASIC_SPEC.md#対応範囲)、[宣言型構成管理](BASIC_SPEC.md#宣言型構成管理内製iac)の解析・観測・差分と計画。
- 完了条件: 本体導入状態と管理状態の分離、三構成からの必須選択、構成の保存・整合性検査、操作状態、排他制御、実行記録を検証でき、読み取り専用操作と変更計画を実行できる。宣言型管理の初期限定対象について、解析・資源識別・管理範囲・差分と計画の契約を確定し、対応する[受入条件](BASIC_SPEC.md#宣言型構成管理の受入条件)を検証できる。

## Phase 3: バイナリ導入と共通の更新・保護・復旧

- 依存: Phase 2。
- 対象: [バイナリ導入](BASIC_SPEC.md#バイナリ導入)、[self](BASIC_SPEC.md#self)、[更新・署名検証](BASIC_SPEC.md#本体の導入更新復旧)、[セキュリティ](POLICIES.md#セキュリティ)、[バックアップ](BASIC_SPEC.md#バックアップとデータ保護)、[宣言型管理の初期限定対象](BASIC_SPEC.md#宣言型構成管理の責務と適用範囲)の適用・再検証・復旧。

## Phase 4: 三構成の導入と機能統合

- 依存: Phase 3。
- 対象: [サーバ構成](server/specification.md)、[マイニング構成](mining/specification.md)、[マスターの機能統合](master/specification.md#機能の統合)、宣言型管理の[段階的な対象拡張](BASIC_SPEC.md#宣言型構成管理の責務と適用範囲)。
- 完了条件: [機能適用の範囲](POLICIES.md#構成の分離)に対応する導入・再実行・検証と、内包機能の呼び出し境界を隔離環境で検証できる。先行する限定対象の検証後、パッケージ・systemdの資源契約と例外条件を確定し、宣言型管理の受入条件を拡張して検証できる。機器固有の導入結果は対応実機で確認できる。物理マスターの構築はPhase 6、SSH管理フローの完成はPhase 7で確認する。

## Phase 5: マイニング運転と自動保守

- 依存: Phase 4。
- 対象: マイニング構成の[監視と自動復旧](POLICIES.md#マイニングの運転監視)、[自動更新と再起動](POLICIES.md#マイニングの自動更新と再起動)、[更新失敗時の復旧](POLICIES.md#マイニングの更新失敗時復旧)。
- 完了条件: 採掘停止、通信断、温度異常、再試行上限、更新失敗を検証でき、CPU・GPU別の運転と構成ポリシーに沿った復旧・更新の共通処理が成立する。更新開始の入口との統合はPhase 6・7に分け、独立したtimer更新を完成条件にしない。

## Phase 6: 外部媒体と物理マスターの構築

- 依存: Phase 5。
- 対象: [外部媒体の導入・保守](BASIC_SPEC.md#外部媒体による導入と保守)、[ISO生成](BASIC_SPEC.md#isoの作成)、[BIOS・UEFI](BASIC_SPEC.md#ファームウェアの検査と設定)、[マスター初期構築](master/specification.md#初期構築)。
- 完了条件: 共通バイナリとハッシュが一致するISOを生成し、VMで外部媒体からの導入・更新・バックアップ・復旧と、[媒体を外した起動・再起動](BASIC_SPEC.md#内蔵osの起動確認)を検証できる。物理マスターの内蔵OSと管理初期設定を構築し、起動後の確認を[構成の検証](master/specification.md#構成の検証)へ照合できる。対応実機では、ファームウェア設定の確認結果と復電起動の確認結果を区別して記録できる。

## Phase 7: マスター経由のCloud自動化

- 依存: Phase 6。
- 対象: [マスター管理](master/specification.md)、[Cloud導入・保守](BASIC_SPEC.md#sshによるcloud環境の導入と保守)、Cloudの[バックアップ](BASIC_SPEC.md#バックアップとデータ保護)。SSH実行環境と既存OSを区別する契約を先に確定し、OS導入から構成・更新・保全までを接続する。
- 完了条件: 内蔵OSで稼働するマスターで対象・操作と必須項目を選択し、SSH経由で自動処理できる。隔離VMの空ディスクへのOS導入と、既存対応OSへの構成・更新・バックアップ、再起動・再接続・中断照合を検証できる。cloud-initや対象VPSでの追加の手動セットアップを必須にしない。

Phase 6・7では、先行フェーズで検証した宣言型管理を各入口から同じCore処理へ接続する。[入口の統合契約](BASIC_SPEC.md#宣言型構成管理の未確定契約)を確定し、対象・計画・操作記録の引き継ぎと中断照合を各フェーズの受入条件に含める。

## Phase 8: 統合検証と初期リリース

- 依存: Phase 7。
- 対象: [テスト体系](BASIC_SPEC.md#テスト体系)、[リリース](BASIC_SPEC.md#リリース)、[アーティファクト検査](BASIC_SPEC.md#アーティファクト検査)。

| 3: 高難易度 | 段階0と、必要な先行契約・隔離環境。該当機能フェーズで個別評価 | 安全性と互換性に必要な試験を完了し、対象OS・機器で成立する範囲を確定できる。未達条件は保留として残る | 未着手 |

各段階は機能フェーズと並行する進捗軸とし、番号の順だけで全機能の抽出を一括実施しない。該当機能が必要とする内製契約・例外選定・検証が未完了なら、その機能フェーズの完了条件は未達とする。Rustの依存検査と仕様追跡はPhase 1の基盤へ組み込み、Phase 8の公開前に対象成果物でも再検証する。
