## 目的と利用

利用者は管理対象を導入・保守する管理者とする。物理PCの外部媒体操作と、物理マスターからのVPS・クラウド管理を利用場面とする。製品名・CLI・Core・媒体・Cloudの用語と境界は[製品構成](#製品構成)、実行側と対象側は[ライフサイクル](#実行側と対象側)を参照する。

### 目的

ServerSeedは、共通基盤を主軸とし、マスター管理構成、マイニング構成およびサーバ構成を同一リポジトリで管理するRust製CLIのライフサイクル管理ツールである。物理サーバ、ミニPC、CPU・GPU搭載PC、VPSおよびクラウド上の対応環境を、共通の定義に基づいてインストール、セットアップ、アップデート、バックアップ、検証および復旧する。

主要な利用者インターフェースは`serverseed`コマンドとする。本体の共通手段は[バイナリ導入](#バイナリ導入)、利用者が操作を開始する場所と通常運用は[実行入口](POLICIES.md#実行入口と通常運用)に従う。事業者との責任境界は[プロバイダー非依存](#プロバイダー非依存)を参照する。

### 基本原則

製品全体の判断基準は[基本方針](PRINCIPLES.md#製品の基本方針)を参照する。

## 対象範囲

### 対応範囲

導入する対象OSと通常運用OSは、三構成ともUbuntu Serverに統一し、初期対応バージョンはUbuntu Server 24.04 LTSに一本化する。導入前のSSH実行環境は[別の能力検査](#cloudの実行環境と対象os)で扱い、[導入対象のOS判定](#ubuntu-2404-lts判定)だけで採否を決めない。

開発フェーズと実施順序は[ロードマップ](ROADMAP.md)を参照する。

Debian、RHEL系、FreeBSD、その他OSは対応対象外とする。将来提案や補助文書で他OS対応を扱う場合も、本仕様が更新されない限りServerSeedの実装対象に含めない。

### プロバイダー非依存

事業者APIとの関係は[プロバイダー非依存](PRINCIPLES.md#プロバイダー非依存)を参照する。

構成を適用する対象OSはプロバイダー名ではなく、次の能力に基づいて判定する。OS導入前の実行能力は[Cloud仕様](#cloudの実行環境と対象os)を参照する。

- Ubuntu 24.04 LTSであること
- systemdが利用可能であること
- SSH管理経路を維持できること
- cloud-initの有無と既存設定（必須機能ではなく保護対象の検査）
- 仮想化環境の有無
- 必要なディスク容量
- 必要な外部通信またはローカル更新元の有無

次はServerSeedの責任範囲外とする。

- VPSまたはインスタンスの作成・削除
- クラウドディスクの作成・追加
- セキュリティグループ操作
- クラウドスナップショット
- 固定IP割り当て
- DNS設定
- ロードバランサー設定
- プロバイダー固有バックアップ
- 課金および契約管理
- プロバイダーAPI認証

## 実行環境

### Ubuntu 24.04 LTS判定

Ubuntu 24.04 LTS対応判定は`/etc/os-release`を主情報とする。

対応OSと判定するには、少なくとも次を満たす必要がある。

```text
ID=ubuntu
VERSION_ID=24.04
```

`VERSION_ID`が`24.04`以外、`ID`が`ubuntu`以外、または`/etc/os-release`を読み取れない場合は対応OSと判定しない。`VERSION_CODENAME`は補助情報として記録できるが、判定の唯一の根拠にしてはならない。

Ubuntu派生OSはUbuntu 24.04 LTSとして扱わない。`ID_LIKE=debian`のみを根拠に対応OSと判定してはならない。

### 対応アーキテクチャ

初期対応アーキテクチャは次とする。

| アーキテクチャ | 用途 |
|---|---|
| `amd64` | 物理サーバ、VPS、クラウドの標準対象 |
| `arm64` | ARMサーバ、ARM対応VPS、将来の物理環境対象 |

マイニング構成の利用条件は[マイニング構成](mining/specification.md#対応範囲)を参照する。

マスター管理構成には[内包機能の対応条件](master/specification.md#対応範囲)も適用する。共通バイナリやISOのCPU対応と、そのCPUで選択構成を導入できることを同一視しない。

対応外アーキテクチャでの実行可否は[対応外アーキテクチャ](POLICIES.md#対応外アーキテクチャ)を参照する。

### Ubuntuパッケージ管理前提

ServerSeedはUbuntu 24.04 LTSの標準パッケージ管理を前提とする。

少なくとも次のコマンドまたは機能が利用可能であることを確認する。

```text
dpkg
apt-get
systemctl
journalctl
sha256sum
gpgv
```

変更操作の実行に必要なコマンドが欠けている場合は、変更を開始せず、必要な不足項目を表示する。

### Rustツールチェーン

採用ツールチェーンと最低対応Rustバージョンは`1.99.1`、editionは`2024`とする。確認日は`2026-10-16`とする。

採用理由は、確認時点の[公式安定版](https://blog.rust-lang.org/2026/10/15/Rust-1.99.1/)を固定して開発・CI間の差異を抑え、[Rust 2024](https://doc.rust-lang.org/edition-guide/rust-2024/index.html)を使用するためとする。最低対応版を採用ツールチェーンと揃え、未検証の旧版への対応は保証しない。

実装開始時に`rust-toolchain.toml`へ本節の採用バージョンを指定し、rustfmtとClippyも同じツールチェーンから使用する。`Cargo.toml`には本節のeditionと最低対応版をそれぞれ`edition`と`rust-version`へ指定する。

内製crateの採用版への対応は[依存条件](POLICIES.md#rustと内製crateの依存条件)に従って確認する。UbuntuとCI上の検証は[配布バイナリのターゲットとリンク](#配布バイナリのターゲットとリンク)および[CI実行環境](#ci実行環境)に従い、ツールチェーンの採用だけで検証済みと扱わない。

## 全体構成

### 製品構成

| 名称 | 役割 |
|---|---|
| ServerSeed | `serverseed` CLIを中心としたシステム全体 |
| ServerSeed CLI | 利用者および自動処理が実行する主要インターフェース |
| ServerSeed Core | 主軸となる共通基盤。CLIから呼び出される導入・保守の共通処理と管理制御 |
| マスター管理構成（master） | [マスター管理構成仕様](master/specification.md) |
| サーバ構成（server） | [サーバ構成仕様](server/specification.md) |
| マイニング構成（mining） | [マイニング構成仕様](mining/specification.md) |
| ServerSeed USB | ISOを書き込んだUSBメモリ等の外部媒体による[物理PCの導入・保守](#外部媒体による導入と保守) |
| ServerSeed Cloud | SSH実行環境と対象OSを区別して、VPS・クラウドを[導入・保守する方式](#sshによるcloud環境の導入と保守) |
| ServerSeed ISO | 共通バイナリを収録した外部媒体用の起動・導入・保守イメージ。検証済みの仮想メディア起動にも使用する |

ISOを独立した共通基盤や構成として実装しない。配布成果物とバイナリの同一性は[リリース工程](#リリース工程)で保証する。

### 実装構成と責任境界

初期実装は単一のCargoパッケージを基本とし、CLIの入口を`src/main.rs`、共通ロジックの入口を`src/lib.rs`に配置する。CLIから各責務のモジュールを呼び出す。

ServerSeed CLIは、入力解析、出力形式、確認プロンプト、終了コード、ロック取得を担当する。

ServerSeed Coreには、CLIから呼び出される環境共通の次の処理を配置する。

- 状態判定
- 構成適用
- 更新
- マイグレーション
- 検証
- ログ
- 署名およびチェックサム検証
- バックアップ前提条件の確認

外部媒体とCloudに固有の起動・搬入処理は共通の適用ロジックから分離し、CLIの入口または内部モジュールから呼び出す。マスターの選択・計画・SSH制御は[マスター管理構成](master/specification.md)が担当し、対象OSの構成適用には共通処理を再利用する。事業者固有機能の扱いは[プロバイダー非依存](#プロバイダー非依存)に従う。

#### 自動処理の責任境界

| 責務 | 正本と実装上の境界 |
|---|---|
| 物理PCの開始と引き継ぎ | [外部媒体](#外部媒体による導入と保守)。Live環境と内蔵OSの処理を識別し、内蔵OSの本体管理・更新には共通ロジックを使う |
| 対象・操作の選択と遠隔制御 | [マスター管理](master/specification.md)。SSHの接続・転送と対象側の検査・変更を分離する |
| 対象のOS導入と構成適用 | [Cloud](#sshによるcloud環境の導入と保守)と[ライフサイクル](#本体の導入更新復旧)。実行環境の状態を対象OSへコピーしない |
| データ取得と保存 | [バックアップ](#バックアップとデータ保護)。制御側、対象データ、保存先を分離し、構成固有の整合性確認へ接続する |

この境界は実装配置の方針であり、遠隔実行のインターフェースや保存形式まで確定するものではない。担当仕様の未確定契約に依存する部分は[着手条件](POLICIES.md#実装着手と仕様充足の判定)を満たすまで実装しない。

#### 宣言型構成管理の責任境界

[内製IaC](PRINCIPLES.md#内製iac)は`src/core/`の責務別内部モジュールとして配置する。定義解析は[共通設定](#構成定義の解析)、資源の観測・差分・計画・適用・再検証は[宣言型構成管理](#宣言型構成管理の処理フロー)へ対応付け、既存の状態判定・排他・操作記録は[共通基盤](#共通基盤と状態管理)を使用する。

CLIは入力と確認・出力を担当し、構成固有モジュールは自身が管理する資源と検証・復旧を共通処理へ接続する。宣言型管理に対して、外部媒体・マスター・SSHの処理は[自動処理の責任境界](#自動処理の責任境界)の入口と制御を担当し、経路別の差分・適用エンジンを作らない。

解析、観測、計画および変更を行う処理の呼び出し境界は、[未確定契約](#宣言型構成管理の未確定契約)の入出力・失敗・副作用の確定時に定める。初期の単一パッケージをIaCの導入だけで分割せず、crate抽出には[差し替え契約](#内製crateの境界と差し替え)を適用する。

#### 内製crateの境界と差し替え

依存の基本境界と内製化の定義は[憲章第7条](CHARTER.md#第7条-提供元依存権利)、宣言・管理への適用は[依存条件](POLICIES.md#rustと内製crateの依存条件)、変更手順は[AGENTS.md](../AGENTS.md#内製化と差し替えの実施手順)、抽出の判断は[段階的な内製化](PRINCIPLES.md#段階的な内製化)を参照する。

内部契約の必須項目は[憲章の内製機能とcrateの完全仕様](CHARTER.md#内製機能とcrateの完全仕様)と[完全仕様の必須条件](POLICIES.md#完全仕様の必須条件)、差し替えの区分は[憲章の定義](CHARTER.md#内製crateの差し替え)を参照する。契約の配置と共通契約の参照は[集約単位](CHARTER.md#第3条-文書の責務と正本)と[憲章第4条](CHARTER.md#第4条-仕様による実装の拘束)へ対応付ける。共通基盤と各構成の所有境界を、crate化だけを理由に変更しない。

呼び出し元と実装の間は責務に必要な公開契約だけで接続し、具体的な実装型、グローバル状態または下位実装の詳細へ直接依存させない。単一パッケージ内のモジュールで契約を検証した後、必要な責務だけをリポジトリ内のcrateとして抽出する。Cargoのpath依存で接続し、パッケージ間の循環参照を作らない。

差し替え前後の同一入力に対する出力・失敗・副作用の照合は[憲章第8条](CHARTER.md#第8条-検証と事実の区別)に従い、移行が必要な場合は対象仕様の互換範囲と移行手順へ対応付ける。テストの配置と追跡形式は[テスト体系](#テスト体系)に従う。

#### 内製機能とcrateの未確定契約

要件単位の標準機能の充足調査と、既存内製機能の再利用評価は未着手とする。具体的な内製対象・実装単位の選定と、担当フェーズの完全仕様・契約ID・承認済み版への対応は未確定であり、標準ライブラリに機能がないことを確認済みとは扱わない。

調査・評価の確認先は[標準機能と内製化の判断](CHARTER.md#標準機能と内製化の判断)、契約の確定と工程通過の確認先は[必須契約](CHARTER.md#内製機能とcrateの完全仕様)と[確認条件](POLICIES.md#内製化と差し替えの確認条件)を参照する。本節の未確定事項を、個別crateの採用・抽出・差し替えが確定した根拠にしない。[要件別の受入・未達参照](#要件別の受入未達参照)と[仕様充足の判定](POLICIES.md#実装着手と仕様充足の判定)へ対応付ける。

審査候補の解析境界と型付き内部APIは[共通validator/実行文脈](complete/PHASE_02.md#スキーマ検証との境界案)、[未封印/封印済み計画](complete/PHASE_03.md#依存と受入の確定候補)、[部分失敗と親操作](complete/PHASE_04.md#データ契約の具体化案)へ一意に対応付ける。各案の旧Value返却APIは並行する契約とせず、担当節の宣言へ集約する。内製化・抽出時の比較対象もその同じ入力/型/エラー/副作用とし、仕様の採用・内製実装・新旧試験成功は未成立のまま区別する。

#### 構成別の責任境界

各構成の入口は`src/profiles/master/`、`src/profiles/server/`および`src/profiles/mining/`へ分離する。[憲章第4条](CHARTER.md#第4条-仕様による実装の拘束)の再利用義務への対応として、マスターは[統合契約](master/specification.md#機能の統合)に沿ってサーバ・採掘の機能を呼び出す。共通の状態判定、機器情報、更新計画、署名検証、ロックおよび履歴はCoreを再利用し、構成固有の導入・検証・復旧は担当機能へ委ねる。

構成間の適用制約は[構成の分離](POLICIES.md#構成の分離)を参照する。

実装はこの構成を起点とし、仕様と矛盾するディレクトリや責務分離を追加しない。

## 運用方式

### 外部媒体による導入と保守

#### 外部媒体の役割

ServerSeed USBは、ISOを書き込んだUSBメモリ等の外部媒体の呼称とし、物理PCおよびベアメタルに対する導入・保守を担当する。使用する媒体形式ごとの書き込み・起動互換性を確認し、すべての外部メモリ機器を無条件に対応済みと扱わない。

- Ubuntu 24.04 LTSのセットアップ
- ServerSeed初期構成
- 管理対象OSのアップデート
- バックアップ
- 状態検査
- 検証
- 復旧支援

通常運用と媒体を外す条件は[実行入口と通常運用](POLICIES.md#実行入口と通常運用)、マスター管理構成を選択した場合の統合手順は[マスター初期構築](master/specification.md#初期構築)を参照する。

#### ISOの作成

ISOはアーキテクチャ別に作成する。`packaging/iso/recipe.yml`に、ベースとなる公式Ubuntu Server 24.04 LTS ISOの正確な版・取得URL・SHA-256、公式署名の検証条件、ServerSeedの固定バージョンと本体ハッシュ、ISO生成ツールとその版を定義する。曖昧な`latest`指定や未検証のベースを使用しない。

生成処理は`release/build-iso`から実行し、固定した`xorriso`とSquashFSの操作ツールをCI用イメージで提供する。ベースISOのブート情報を維持して、検証済み本体、導入テンプレートおよび起動用unitを組み込み、USBへのイメージ書き込みと仮想光学メディア起動の両方を検証する。本体をISO向けに再ビルドせず、[リリース工程](#リリース工程)の同じ成果物を使う。

起動用unitは同梱バイナリの実行時依存と検証ツールを使用できるLive環境で`serverseed`を開始する。Subiquityの無確認な先行実行を抑止し、[セットアップ](#外部媒体のセットアップ)の確認前にOS導入を開始しない。対応する起動方式とSecure Bootの扱いは[ISOの起動互換性](#isoの起動互換性)に従う。

#### 同梱本体の固定

収録版、起動時の検証、取得とオフラインの制約は[USB起動と取得](SECURITY_POLICY.md#usb起動と取得)を参照する。

#### 外部媒体の使用方法

ServerSeed USBでは、起動時に`serverseed`を自動実行し、対象検査と操作の選択へ進む。適用の自動化は[必須選択と自動実行](POLICIES.md#必須選択と自動実行)に従う。

「USB接続」は、稼働中のOSへ挿した瞬間に処理を開始することではなく、準備した外部媒体を接続して物理PCを起動または再起動することと定義する。

標準操作は次のとおりとする。

1. 対象PCを停止する。
2. 検証済みのServerSeed外部媒体を接続する。
3. 外部媒体から起動する。
4. ServerSeedが内蔵ストレージを検査する。
5. 状態に応じて操作候補を提示し、利用者が操作・必要入力を選択する。初期セットアップの構成選択、更新・復旧での保存済み構成の継承は[構成選択](POLICIES.md#構成選択と継続管理)に従う。
6. 計画の確認と前提検査後、選択済み処理を自動実行し、結果を検証する。
7. 処理終了と媒体の安全な取り外しを案内し、[内蔵OSの起動確認](#内蔵osの起動確認)へ進む。

#### 外部媒体起動時の分岐

状態に応じた動作は[USB起動時の分岐](POLICIES.md#usb起動時の分岐)を参照する。

#### 外部媒体のセットアップ

初期セットアップの構成選択は[初期構成選択と継続管理](POLICIES.md#構成選択と継続管理)に従う。対象SSDの表示情報と全消去の確認は[CLIの確認方式](#ディスク消去の確認表示)に従う。

必須の選択・入力と対象ディスクの確認を完了し、消去を伴う場合はその追加確認を経て、次を自動実行する。既存の対応OSを取り込む場合はOSインストールとディスク消去を省き、確認した取り込み計画だけを適用する。

1. Ubuntu 24.04 LTSのインストール
2. 管理ユーザーの作成
3. SSH公開鍵の登録
4. [SSH安全条件](SECURITY_POLICY.md#セキュリティの共通条件)の適用
5. SSH鍵接続の確認と認証設定の検証
6. OS更新および基本パッケージ導入
7. ファイアウォールおよび基本セキュリティ設定
8. Tailscaleの導入
9. [機能の適用範囲](POLICIES.md#構成の分離)に従う選択済み構成の導入。マスター固有の統合・初期設定は[担当手順](master/specification.md#初期構築)を使用
10. 共通および構成固有のバックアップ、ログおよび監視設定
11. 選択済み構成を含むServerSeed管理情報の作成
12. 最終検証およびレポート作成

Ubuntuの導入設定は確認済みの対象ディスク情報からLive環境の`/autoinstall.yaml`へ生成し、その後に対応版のSubiquityを開始する。このファイル名は[Ubuntuインストーラーの外部契約](https://canonical-subiquity.readthedocs-hosted.com/en/latest/tutorial/providing-autoinstall.html)に従う。ISOのルートに消去対象入りの自動認識ファイルをあらかじめ置かない。

新OSへ収録版の本体を導入し、マウントした新OS内で[共通の導入処理](#バイナリ導入)を呼び出す。実行中Live環境の導入情報・ロック・マシン識別情報を新OSのものとしてコピーしない。対象OS内での処理とLive環境側の制御は同じ操作として直列化し、内蔵OSの管理記録を最終検証後に確定する。

対話認証の実施時期は[USBの対話認証](SECURITY_POLICY.md#usbの対話認証)に従う。

#### 外部媒体による更新・バックアップ・復旧

操作ごとに対象と保存済み構成を照合し、更新は[更新処理](#更新処理)、バックアップは[実行と保存先](#バックアップの実行と保存先)、復旧は[recover](#recover)を使用する。`MANAGED`の検出だけで更新を開始したり、バックアップ要求を更新へ置き換えたりしない。

Live環境から内蔵OSのファイルを操作する工程と、対象OS内でサービス・パッケージを扱う工程を区別する。後者への引き継ぎ、再起動前後の同一対象・計画・ロックと記録の照合、停止したアプリデータのバックアップ整合性、媒体取り外し時の書き込み完了確認の具体契約は未確定とする。既存のローカル`update`をLive環境へ実行するだけで、内蔵OSを更新した扱いにしない。

これらの契約と[対象別のバックアップ契約](#バックアップの未確定契約)が確定するまで、依存する保守機能を実装着手可能と判定しない。

#### 外部媒体の自動化条件

構成選択と自動実行の条件は[構成選択と継続管理](POLICIES.md#構成選択と継続管理)、確認の表示・入力は[CLIの確認方式](#ディスク消去の確認表示)を参照する。

ディスク操作の許可条件は[ディスク操作](POLICIES.md#ディスク操作)に従う。

#### 外部媒体の論理構成

論理構成は次を基本とする。

```text
SERVERSEED/
├── boot/
├── installer/
│   ├── Ubuntu installer
│   └── autoinstall.yml
├── repository/
├── serverseed/
│   └── release/
│       ├── serverseed_VERSION_linux_ARCH
│       ├── serverseed_VERSION_build.json
│       ├── serverseed_VERSION_manifest.json
│       └── serverseed_VERSION_manifest.json.asc
└── boot-metadata/
```

`installer/autoinstall.yml`は導入設定のテンプレートであり、対象ディスクを確定した設定ではない。確認済みの情報から実行時に生成する設定とその配置先は[セットアップ](#外部媒体のセットアップ)を参照する。

`ARCH`は当該媒体のアーキテクチャとする。本体用マニフェストは他CPUのエントリを含められるが、実行するCPUの本体と必要な検証情報だけを収録する。`repository/`には配布条件を確認した導入・復旧資材だけを置く。Ubuntu固有の`casper/`、ブートローダー等の構造も維持する。

USBボリュームラベルは`SERVERSEED`とする。収録を禁止する情報は[USB起動と取得](SECURITY_POLICY.md#usb起動と取得)に従う。

#### 媒体マニフェスト

ISOの外側に置く媒体マニフェストは、少なくとも次の形式とする。

```json
{
  "schema_version": 1,
  "serverseed_version": "0.1.0",
  "binary_manifest_sha256": "hex",
  "artifacts": [
    {
      "type": "iso",
      "architecture": "amd64",
      "path": "serverseed_0.1.0_usb_amd64.iso",
      "sha256": "hex",
      "size": 123456789,
      "embedded_binary_sha256": "hex",
      "base_iso_sha256": "hex",
      "recipe_sha256": "hex",
      "boot_modes": ["uefi", "bios"],
      "secure_boot": "not_verified"
    }
  ]
}
```

例は一件を抜粋しており、ハッシュとサイズは形式例とする。実配布ではアーキテクチャごとに一件とし、`type`は`iso`に固定する。`path`、`size`、ハッシュの制約は[本体マニフェスト](#更新マニフェスト)と同じ定義を参照する。欠損、未知の版・型、重複エントリ、CPUや収録版の不一致を拒否する。

`binary_manifest_sha256`は収録した本体マニフェスト、`embedded_binary_sha256`はそのCPUの本体を指す。両者が本体マニフェストと一致することを生成後に検証する。ベースISOと生成定義のハッシュも保持し、ISO内には自身の外部マニフェストを収録しない。

`boot_modes`と`secure_boot`の値・検証条件は[ISOの起動互換性](#isoの起動互換性)に従う。これらは試験結果であり、初期の仕様段階で実機対応済みと記載しない。

#### USBの作成と交換

管理端末で信頼鍵、媒体マニフェストの署名、ISOのハッシュ・サイズを確認し、書き込み対象USBの機種・容量・識別情報を確認する。書き込みはUSB全体を消去する操作として[破壊的操作の確認](#ディスク消去の確認表示)を必要とし、デバイス名だけで対象を選ばない。

検証済みISOをイメージ書き込みツールでUSBへ書き込み、ISOと同じ長さの書き込み領域を読み戻して照合する。対象の除外条件は[ディスク操作](POLICIES.md#ディスク操作)に従う。媒体の正式性と交換単位は[USB媒体の更新](POLICIES.md#usb媒体の更新)に従う。

#### 外部媒体自体の更新

媒体の更新場所、交換後の扱いと旧版使用の制約は[USB媒体の更新](POLICIES.md#usb媒体の更新)を参照する。

### SSHによるCloud環境の導入と保守

#### Cloudの役割

ServerSeed Cloudは、マスターからSSHで到達したVPS・クラウドの実行環境を使い、対象OSの導入、構成適用および保守を行う。選択・接続・結果照合の制御は[マスター管理](master/specification.md#自動処理の流れ)、共通の適用処理は[ライフサイクル](#本体の導入更新復旧)が担当する。

本節はSSH先の実行環境と対象ストレージに対する処理を定義する。

#### Cloudの前提

接続前提と管理経路の保護は[Cloudの管理経路](SECURITY_POLICY.md#cloudの管理経路)、自動化の判断基準は[Cloud導入](PRINCIPLES.md#cloud導入)を参照する。

VPSへのISO取得・接続やコンパイラー・Cargoの導入は要求しない。cloud-initの有無によって対象を除外せず、既存設定の扱いは[cloud-init](POLICIES.md#cloud-init)に従う。

構成選択と非対応時の停止は[構成選択と継続管理](POLICIES.md#構成選択と継続管理)に従う。接続先には[共通の対応範囲](#対応範囲)だけでなく、[構成ごとの担当仕様](#製品構成)の対応条件も照合する。マスター管理構成を選択した場合も[マスターの対応範囲](master/specification.md#対応範囲)を適用し、Cloudからの選択を対応範囲の拡張や[構築条件](POLICIES.md#実行入口と通常運用)の代替と扱わない。

#### Cloudの実行環境と対象OS

「実行環境」はSSHサーバと導入・保守処理が動く環境、「対象OS」は管理対象ストレージ上の導入済みまたは導入予定OSとする。レスキュー・一時環境から接続する場合、両者は異なる。対象OSのないディスクでも、SSHの実行環境が用意されていれば検査対象に含める。

接続後、次を操作別に検査し、取得した情報を実行環境と対象へ分けて計画に対応付ける。

| 検査 | 対象 |
|---|---|
| 実行能力 | 実行環境のOS・CPU、利用可能コマンド、必要な権限、署名検証・転送・導入ツールと実行時依存 |
| ストレージ | 実行環境のルート・マウント・使用中ディスク、導入先の機器識別・容量・内容、バックアップ先との区別 |
| 起動・再接続 | 対象のブート方式、ブートローダーの設置能力、導入後のネットワーク・SSH到達経路、管理先の識別と復旧経路 |
| 対象OS | [共通状態判定](#共通状態判定)、導入済みOSへの[対応判定](#ubuntu-2404-lts判定)、構成適用時のsystemdと[必要機能](#ubuntuパッケージ管理前提) |

SSH実行環境の`/etc/os-release`を対象OSの情報として代用せず、空ディスクを接続先ルートと同一視しない。実行環境がUbuntu以外の場合の使用可否は下記の未確定契約へ対応付け、任意のOS・SSH実装を利用可能と判定しない。

#### CloudへのOSインストール

OSのない対象に対しては、次の順序で処理する。対象の判定は[状態判定の優先順位](#状態判定の優先順位)に従う。

1. 実行環境と対象を検査し、OS導入と再接続までの実行能力を確認する。
2. マスターへ対象ディスクと導入予定の[対応OS](#対応範囲)、データへの影響、保全・起動・再接続の計画を返す。
3. マスターで確定した必須選択・破壊的操作の確認と計画を受け、適用直前に対象を再照合する。
4. 検証済みのOS資材を用いて対象へOSを導入し、ブートローダー、管理ユーザー、公開鍵と接続用ネットワークを構成する。
5. 対象ストレージから起動し、マスターから再接続して同じ対象と導入結果を確認する。
6. 本体の導入と初期セットアップへ進む。

OS導入機構、必要資材、接続先変更と識別検証の詳細は[未確定契約](#cloudの未確定契約)とする。能力が不足・不明な接続先へ、単にSSHへ接続できたことを根拠に処理を適用しない。

#### Cloudへの本体導入

対象OSが対応OSとして起動している場合は、OS導入を挟まず本段階へ進める。マスターが固定した署名付き本体と検証情報を転送または対象から取得し、[初回の取得と配置](#初回の取得と配置)を対象OS内で自動実行する。取得処理と[実行時依存](#本体ビルドメタデータ)を検証する。

一時実行環境へ搬入した本体と、対象OSへ配置した本体の導入情報を取り違えない。呼び出しと操作記録は[実行側と対象側](#実行側と対象側)に従う。

#### Cloudの初期セットアップ

`ADOPTABLE`状態の対応OSに対して、次を行う。

1. マスターで選択した構成・入力・計画の照合と、対象OS、systemd、ネットワークおよび空き容量の検査
2. 現在のSSH接続および管理ユーザーの保護
3. 基本セキュリティ設定
4. 選択済み構成に必要なパッケージおよび実行基盤の導入
5. バックアップ、ログおよび監視設定
6. ServerSeed管理情報の作成
7. 最終検証

既存管理経路とルートディスクの保護は[Cloudの管理経路](SECURITY_POLICY.md#cloudの管理経路)に従う。

#### Cloudの更新とバックアップ

マスターが確定した処理内で、構成・OS更新は[更新処理](#更新処理)、本体変更は[self](#self)、バックアップは[実行と保存先](#バックアップの実行と保存先)を使用する。対象VPSでの追加の手動開始を要求しない。更新後の再起動・再接続も計画に含める。

#### Cloudの起動不能時の復旧

対象OSを起動できなくてもSSHの一時実行環境が利用できれば、マスターから対象を再検査して復旧計画を作成する。SSH自体が利用不能なら接続経路の準備を利用者へ案内し、再接続できるまで対象の変更処理へ進まない。事業者側のレスキュー起動・仮想メディア接続は、[責任範囲外の資源操作](#プロバイダー非依存)を自動化する根拠にしない。

設定復元・起動修復の範囲は[recover](#recover)、OS再導入は独立したOS導入計画として区別する。バックアップからの復元は[復元確認](#バックアップの復元確認)とその未確定契約へ対応付ける。

#### Cloudの未確定契約

| 対象 | 未確定の内容 |
|---|---|
| SSH実行環境 | 対応OS・CPU・実行コマンド、必要権限、起動環境の準備と利用条件。マスター側の接続・認証・制御契約は[担当仕様](master/specification.md#未確定契約)へ集約 |
| OS導入方式 | 採用インストーラー・資材・固定版、ストレージの識別・除外・マウントと書き込み、ブート構成、入力・出力・失敗位置、適合する例外ID |
| 再起動と再接続 | 導入後の接続設定の生成・検証、対象の同一性とホスト鍵変更の確認、待機・時間制限・再試行、到達不能時の保全・復旧 |

これらの未確定部分に既存の`setup`や[Ubuntu対応判定](#ubuntu-2404-lts判定)だけを流用して、導入可能・実装着手可能とは判定しない。

### ファームウェアの検査と設定

#### ISOの起動互換性

初期のISO検証対象は次のとおりとする。

| アーキテクチャ | 起動方式 |
|---|---|
| `amd64` | UEFI、Legacy BIOS |
| `arm64` | UEFI |

媒体マニフェストの`boot_modes`は、成功した方式を`uefi`または`bios`で記録する。要求起動方式に対する公開条件は[公開前の検証](SECURITY_POLICY.md#公開前の検証)を参照する。機種固有のファームウェアやブート方式を必要とするARM機器は、UEFIサーバ向けISOの成功から対応を推測しない。

`secure_boot`は`verified`、`not_verified`、`not_supported`とする。OpenPGPによる配布物の真正性確認とUEFI Secure Bootは別の検証である。`verified`は有効状態でのブートチェーン・カーネル・本体起動を検証した対象に限り、対象ファームウェアと試験結果を配布メタデータへ付ける。無効状態での試験だけで対応を保証しない。

有効状態を確認できない場合の案内と設定変更の制約は[ファームウェア操作](SECURITY_POLICY.md#ファームウェア操作)を参照する。

#### 内蔵OSの起動確認

[媒体なしの通常運用](POLICIES.md#実行入口と通常運用)の受入確認は、導入・保守の処理終了と安全な取り外しを確認した後、外部媒体を接続せずに行う。

1. 内蔵ストレージのブートローダーとルートファイルシステムからOSが起動することを確認する。
2. 媒体上のブート項目・設定・実行本体やマウント待ちを必要とせず、通常サービスが起動することを確認する。
3. 媒体を接続しないままOSを再起動し、同じ条件で運用へ戻ることを確認する。
4. マスターの場合は、内蔵OS上で[構成の検証](master/specification.md#構成の検証)へ照合し、SSH管理の入口を含む内包機能の起動・準備状態を確認する。

ISOの起動成功と内蔵OSの起動成功を別の検証結果として扱う。媒体を外した起動・再起動を未試験の場合は受入未完了とし、仮想メディアを接続したままのVM試験で代替しない。接続先を変更するCloudの再起動検証は[Cloud仕様](#cloudへのosインストール)を参照する。

#### ファームウェア操作の参照

検査・自動化の基本的な扱いは[ファームウェア自動化](PRINCIPLES.md#ファームウェア自動化)を参照する。

状態別の操作可否は[ファームウェア操作](SECURITY_POLICY.md#ファームウェア操作)を参照する。

#### ファームウェアの自動化対象

対応するUEFI環境では次を自動化できる。

- UbuntuのUEFI起動項目作成
- ブートローダー登録
- 起動順序の検査および変更
- 次回起動先の指定
- 不要な起動項目の検査

#### 推奨起動順序

推奨起動順は、ServerSeed USB、内蔵SSD、その他の順とする。USBが存在しなければ内蔵SSDから通常起動する。

#### ファームウェアの手動設定

次は機種依存のため、初回に手動設定が必要となる場合がある。

- UEFIモード
- USB Boot
- USBを内蔵SSDより優先する起動順序
- Secure Boot
- 停電復旧後の自動電源ON
- 仮想化機能
- Wake on LAN
- TPM
- ストレージモード

推奨起動順は[推奨起動順序](#推奨起動順序)を参照する。

変更を禁止する項目も[ファームウェア操作](SECURITY_POLICY.md#ファームウェア操作)を参照する。

#### 機種別の自動設定と復電確認

機種と利用可能な公式操作手段を検出し、対応する場合は復電時の自動電源投入、Wake on LANなど選択済みポリシーに必要な項目を自動設定する。現在値の記録、変更、読み戻し確認、再起動要否の記録を行う。メーカー・機種別処理はplatform配下で共通制御から分離する。操作可否は[ファームウェア操作](SECURITY_POLICY.md#ファームウェア操作)に従う。

項目別に成功、失敗、非対応、未確認を記録する。設定値の確認と実際の復電起動テストは区別し、実機テスト未実施なら「設定済み・復帰動作未確認」とする。OS全体の停止や完全電源断からの復帰は、対応ハードウェアと設定が確認できた範囲のみ提供し、すべての機種での復帰を保証しない。

#### ファームウェアの未確定契約

上記の自動化対象と確認項目に対し、次の具体契約は未確定とする。

| 対象 | 確定が必要な内容 |
|---|---|
| 対応と操作手段 | 対応機種・ファームウェア版、検出方法、利用する標準・メーカー公式インターフェース、呼び出し条件と外部実行物の採用情報への対応 |
| 設定と確認 | 項目ごとの入力・許容値、現在値の取得・記録、変更・読み戻しの手順、再起動要否と項目別結果の具体的な出力・保存形式、手動確認への引き継ぎ |
| 中断と復旧 | 操作の時間制限、失敗・中断時の停止位置、変更済み項目の照合、再実行・復旧可能範囲と受入検証 |

操作の許可・禁止は[ファームウェア操作](SECURITY_POLICY.md#ファームウェア操作)、外部実行物の個別採用情報は[例外台帳](DEPENDENCY_EXCEPTIONS.md)を参照する。対応対象や設定値を推測で補完せず、依存する実装の着手可否は[仕様充足の判定](POLICIES.md#実装着手と仕様充足の判定)へ照合する。

実機検証の要求とVM専用規定の適用境界に残る未確定条件は、[検証環境の未確定条件](SECURITY_POLICY.md#検証環境の未確定条件)を参照する。

### CLI

#### コマンド

共通コマンド名は`serverseed`とする。ServerSeedの初期提供形態はCLIであり、すべての主要操作は`serverseed`サブコマンドとして提供する。

CLIの提供価値と強化対象は[CLIの強化](PRINCIPLES.md#cliの強化)を参照する。

```bash
serverseed inspect
serverseed setup
serverseed update
serverseed recover
serverseed verify
serverseed report
serverseed status
serverseed version
serverseed doctor
serverseed plan
serverseed support-bundle
serverseed self install
serverseed self update
serverseed self uninstall
```

| コマンド | 役割 |
|---|---|
| `inspect` | OS、ストレージ、BIOS、USBおよび環境を検査 |
| `setup` | 対応環境を初期構築 |
| `update` | 管理対象サーバを更新 |
| `recover` | 起動修復または設定復元 |
| `verify` | セキュリティ、サービスおよびデータ保護状態を検証 |
| `report` | 実行結果と履歴を表示 |
| `status` | 現在の総合状態を表示 |
| `version` | ServerSeed、OSおよび構成バージョンを表示 |
| `doctor` | ServerSeed自身の導入状態、設定、権限、依存コマンドを診断 |
| `plan` | 変更操作の実行計画だけを作成 |
| `support-bundle` | 調査用情報を秘密情報を除外して収集 |
| `self` | 本体だけの導入・更新・削除 |

変更操作の利用者向け入口は[運用条件](POLICIES.md#実行入口と通常運用)、担当手順は[USB導入](#外部媒体による導入と保守)、[マスター管理](master/specification.md)と[Cloud導入](#sshによるcloud環境の導入と保守)を参照する。上記の変更コマンドは、確定した計画を対象OSで実行する共通処理として使用し、対象VPSでの手動入力を追加の工程にしない。破壊的操作の確認は[確認方式](#ディスク消去の確認表示)に従う。

#### 自動化入口のCLI契約

外部媒体の操作選択とマスターの対象・操作選択を同じ既存コマンドの引数で表現済みとは扱わない。次の契約は未確定であり、具体的なコマンド名・オプション・JSONフィールドを追加したり、未定義の`master`・`backup`コマンドを実装したりしない。

| 対象 | 確定が必要な内容 |
|---|---|
| 外部媒体の開始 | 起動用unitから選択画面への起動方法、操作・対象の入力、構成の選択、内蔵OSへの引き継ぎ |
| マスターの開始 | [マスター固有のCLI](master/specification.md#マスター固有のcli)で定義する入力・出力と、共通CLIの契約との接続 |
| バックアップ・復元 | 独立操作と更新内の工程の区別、対象・保存先・復元元の指定、確認と成功・失敗の出力 |
| 自動実行の受け渡し | 選択結果・対象・計画・操作IDの対応、確認済み範囲の検証、権限・排他と重複実行防止 |

全構成で使用する入力形式は[共通オプション](#共通オプション)、終了コードは[終了コード](#終了コード)、構造化出力は[共通JSON出力](#共通json出力)、マスター固有の入力と制御・設定は[担当仕様](master/specification.md)、共通の構成記録は[基本設定](#configyml)を正本とする。未定義の動作を既存の終了コードやJSON例へ独断で割り当てず、[仕様充足](POLICIES.md#実装着手と仕様充足の判定)を確認してから実装する。

#### コマンドの変更可否

各コマンドの変更可否と読み取り専用の意味は[コマンド別の変更可否](POLICIES.md#コマンド別の変更可否)を参照する。

`verify`で修正の必要性を検出した場合は、必要な操作をレポートする。

#### `self`

`self`は実行中OSの本体を管理する。対象ディスクへのOS導入は行わず、外部媒体・Cloudのセットアップでは同じ導入処理を対象OS内で呼び出す。各操作の状態は[本体導入と構成管理](#本体導入と構成管理)、配置手順は[バイナリ導入](#バイナリ導入)に従う。

| 操作 | 入力と条件 |
|---|---|
| `self install` | ローカルの検証済み本体から実行する。`--source DIR`、`--release-version VERSION`、`--keyring PATH`を必須とする。本体未導入、または導入情報が一致する同一版だけを受け入れる |
| `self update` | `--source DIR_OR_HTTPS_URL`と`--release-version VERSION`を必須とする。整合する導入情報が必要で、管理構成の有無にかかわらず本体だけを更新する |
| `self uninstall` | 導入済み本体の配置情報から削除対象を確定する。削除条件は[本体だけの削除](POLICIES.md#本体だけの削除)に従う |

`--source`は[成果物一式](#リリース)を置くローカルディレクトリまたはHTTPSの基点URLを指定する。`--release-version`はタグの先頭`v`を除いたバージョンを指定し、マニフェスト・本体との不一致を拒否する。`--keyring`は初回に外部確認した公開鍵リングであり、秘密鍵を受け取らない。導入済み本体の更新・復旧は保存済みの信頼鍵を使用する。

`self`の状態別の実行条件は[状態別の実行条件](POLICIES.md#状態別の実行条件)に従う。

`self`の`--dry-run`と`plan`の検査範囲は[計画時と実行時の検証](#計画時と実行時の検証)に従う。`plan self install`、`plan self update`、`plan self uninstall`も各操作と同じ入力を受け付ける。

構成セットアップ前の診断では、設定・構成未作成を`setup_required`として示し、構成値を補完しない。本体・導入情報・権限の不整合は失敗として区別する。初回取得が未完了の段階はシェルからの検証手順を使用し、未導入の`serverseed`を呼び出す前提にしない。

#### `inspect`

`inspect`は対象環境の事実を収集し、推奨状態を判定する。検査中の通信・変更の制約は[読み取り専用検査](POLICIES.md#読み取り専用検査)に従う。

収集対象は次を基本とする。

- OS情報
- カーネル
- systemd状態
- ストレージ情報
- ファイルシステム
- ブート方式
- ネットワークインターフェース、アドレスおよび経路などのローカル情報
- SSH設定
- Docker導入状態
- ServerSeed管理情報

到達性の報告基準も[読み取り専用検査](POLICIES.md#読み取り専用検査)を参照する。

マスターが別処理として確立するSSH接続と、対象側で動く`inspect`のローカル検査を区別する。遠隔制御を追加する理由で`inspect`自身に接続・認証・転送や管理記録の更新を行わせない。SSH経由で呼び出す制御の入力・出力は[自動化入口のCLI契約](#自動化入口のcli契約)の未確定部分として扱う。

#### `setup`

`setup`の状態別の実行条件は[状態別の実行条件](POLICIES.md#状態別の実行条件)に従う。

環境別の処理は[USBのセットアップ](#外部媒体のセットアップ)と[Cloudの初期セットアップ](#cloudの初期セットアップ)に従う。

構成の選択・未選択時の停止は[構成選択と継続管理](POLICIES.md#構成選択と継続管理)、構成値と型は[基本設定](#configyml)を参照する。診断・計画・実行結果で選択済み構成を表示する際は、[管理記録との対応](#構成選択結果と管理記録)に従う。

#### `update`

`update`の状態別の実行条件は[状態別の実行条件](POLICIES.md#状態別の実行条件)に従う。

更新前検査に失敗した場合は変更を開始しない。更新開始後に失敗した場合は失敗状態を記録し、後続処理を停止する。

`--source`と`--release-version`を指定する場合は[self](#self)と同じ定義を使用し、両方を指定する。両方を省略した場合は[候補の固定](POLICIES.md#候補の固定)に従う。`plan update`も同じ入力を受け付ける。

#### `recover`

`recover`の状態別の実行条件は[状態別の実行条件](POLICIES.md#状態別の実行条件)に従う。

復旧の許可範囲は[ロールバック](POLICIES.md#ロールバック)に従う。

`recover --self`は[本体の置換と復旧](#本体の置換と復旧)の退避・中断記録を対象とし、構成やOSの復旧と区別する。配置本体を実行できない場合は、別途検証した同じバージョンまたは互換性のある復旧用バイナリを絶対パスで実行する。取得元を変更する場合も署名・互換性検証を省略しない。

初回導入の中断で保存済みキーリングがまだ存在しない場合だけ、初回と同じ独立確認を済ませた`--keyring PATH`を要求する。保存済みキーリングがある場合の差し替えや、検証失敗を回避する指定には使用しない。

#### `report`

`report`は直近の操作、検査結果、検証結果、失敗理由、再起動要否、次に必要な手動操作を表示する。

人間向け出力では要約を優先する。JSON出力は[共通JSON出力](#共通json出力)に従う。

#### `version`

`version --json`の`data.binary`には、実行本体の`serverseed_version`、`architecture`、収録した`config_revision`・`migration_revision`、および`compatible_config_revision`・`compatible_migration_revision`を出力する。互換範囲は[本体マニフェスト](#更新マニフェスト)と照合する。

対象OSへ適用済みの情報は`data.applied`として分離し、構成未セットアップなら`null`とする。自己申告と署名検証の関係は[信頼鍵の初回導入と更新](SECURITY_POLICY.md#信頼鍵の初回導入と更新)に従う。

#### `doctor`

`doctor`はServerSeed自身の導入状態を診断する。

診断対象は次を基本とする。

- `serverseed`バイナリの存在と実行権限
- 本体導入情報と配置本体のハッシュ・バージョンの一致
- Ubuntu 24.04 LTS判定
- 対応アーキテクチャ判定
- 必須外部コマンドの存在
- `/etc/serverseed/`、`/var/lib/serverseed/`、`/var/log/serverseed/`の存在と権限
- 設定ファイルの構文と型
- 管理マーカーの整合性
- ロックファイルと実行中操作の状態
- 信頼鍵リングの存在
- ログ書き込み可否

`doctor`の変更可否は[コマンド別の変更可否](POLICIES.md#コマンド別の変更可否)に従う。修正候補がある場合は、必要な操作と影響範囲を表示する。

ログ書き込み可否は保存先と親ディレクトリの所有者・権限、ファイルシステムの読み取り専用属性など、読み取れるメタデータから診断する。試験用ファイルの作成・削除やログへの追記は行わない。実際の書き込み成功を保証する診断とは区別し、必要な情報を確認できない場合は理由を添えて`unknown`とする。中断検出と記録先は[読み取り専用時の記録処理](#読み取り専用時の記録処理)に従う。

構成未選択の扱いは[self](#self)に従う。診断結果の`data`に`installation_status`と`setup_required`を含める。前者は`absent`、`installed`、`removed`、`inconsistent`、`pending`、後者はbooleanとする。

`doctor --transaction OPERATION_ID --json`は、本体変更処理が呼び出す読み取り専用の診断モードとする。root権限、保持中の共通ロック、実行中操作・トランザクションのID一致、署名付き候補の検証と実配置ハッシュの一致を確認し、置換直後の導入情報が未確定でも`pending`として候補を検査する。ロック保持プロセスとその診断子プロセスの対応も確認し、条件不成立を通常診断への無条件な成功扱いにしない。このモードは状態や導入情報を確定・修正しない。

#### `plan`

`plan`は`setup`、`update`、`recover`、`recover --self`および[self](#self)の実行計画だけを作成する。

```bash
serverseed plan setup
serverseed plan update
serverseed plan recover
serverseed plan recover --self
serverseed plan self update --source DIR_OR_HTTPS_URL --release-version VERSION
```

`plan`の検査範囲は`--dry-run`と同じとし、[変更操作](POLICIES.md#コマンド別の変更可否)は行わない。本体の取得・検証を含む計画は[計画時と実行時の検証](#計画時と実行時の検証)、中断検出時の扱いは[読み取り専用時の記録処理](#読み取り専用時の記録処理)を参照する。計画の保存は[成果物の保存](POLICIES.md#成果物の保存)に従う。`blocked_by`がある場合は実行不能理由を表示する。

#### `support-bundle`

`support-bundle`は障害調査に必要な情報を収集する。

収集対象は次を基本とする。

- `serverseed version --json`
- `serverseed status --json`
- `serverseed inspect --json`
- `serverseed doctor --json`
- 直近の`operation.json`
- 直近の`history.jsonl`
- ServerSeedログ
- 設定ファイルの秘密情報マスク済み内容

収集時の秘匿化と除外条件は[秘密情報](SECURITY_POLICY.md#秘密情報)に従う。

出力形式はtar.gzとし、ファイル名は次を基本とする。

```text
serverseed-support_MACHINEID_TIMESTAMP.tar.gz
```

この形式例だけでは確定しない収集・保存・出力の契約は、[共通CLIの未確定契約](#共通cliの未確定契約)を参照する。

#### 共通オプションと出力

入力は[共通オプション](#共通オプション)、標準出力の共通条件は[共通JSON出力](#共通json出力)を参照する。

#### 起動時の応答

起動時の入力と応答は次のとおりとする。終了区分に対応する数値は[終了コード](#終了コード)を参照する。

| 入力 | 応答 | 終了区分 |
|---|---|---|
| `--help`またはサブコマンドの`--help` | 対応するヘルプを表示 | 成功 |
| 引数なし、必須入力の不足、未知のコマンド・オプション、引数の不正 | 入力エラーを表示し、不足時は対応するヘルプも案内 | 引数または設定エラー |
| 入力は妥当だが対象機能が未実装 | 未実装であることを表示し、変更を開始せず停止 | 安全確認失敗 |

未実装機能を成功として扱わず、`--json`指定時は[共通JSON出力](#共通json出力)の`result`を`blocked`とし、停止理由を`errors`へ含める。

#### 共通オプション

確認が必要となる操作は[確認方式](POLICIES.md#確認方式)を参照する。

初期実装で共通対応するオプションは次のとおりとする。

```bash
--json
--dry-run
--yes
--config PATH
--log-level LEVEL
--no-color
--output PATH
```

`--yes`の確認省略条件と対話不能時の停止条件は[対話確認と省略](POLICIES.md#対話確認と省略)を参照する。

`--no-color`は人間向け出力の色付けを無効化する。`--json`指定時は常に色付けしない。

#### 成果物の保存

`--output PATH`と`--dry-run`の保存条件は[成果物の保存](POLICIES.md#成果物の保存)を参照する。

#### 共通JSON出力

すべてのコマンドは、標準出力に人が読む要約を出し、`--json`指定時は次の基本形による機械処理用JSONを出力する。

```json
{
  "schema_version": 1,
  "command": "inspect",
  "result": "success",
  "started_at": "RFC3339",
  "finished_at": "RFC3339",
  "state": "MANAGED",
  "summary": "string",
  "data": {},
  "warnings": [],
  "errors": []
}
```

`result`は`success`、`failed`、`blocked`のいずれかとする。`errors`が空でない場合、終了コードは`0`にしてはならない。

人間向け出力とJSON出力の内容は意味的に一致させる。JSON出力時に進捗ログを標準出力へ混在させてはならない。進捗やログは標準エラーまたはログファイルへ出力する。

#### ディスク消去の確認表示

確認の要否と許可条件は[確認方式](POLICIES.md#確認方式)に従う。

ディスク消去を伴う場合、ServerSeedは次の情報を表示する。

- デバイスパス
- メーカー
- モデル
- 容量
- シリアル番号
- 消去されるパーティション一覧

利用者は表示された確認文字列を正確に入力する必要がある。確認文字列には対象ディスクのシリアル番号またはServerSeedが生成した短い確認コードを含める。

#### ログの参照

ログの形式と保存先は[共通基盤のログ形式](#ログ形式)、操作別の記録先は[読み取り専用時の記録処理](#読み取り専用時の記録処理)を参照する。

#### 終了コード

CLIの終了コードは次を基本とする。

| 終了コード | 意味 |
|---|---|
| 0 | 成功 |
| 1 | 一般エラー |
| 2 | 引数または設定エラー |
| 3 | 安全確認失敗、未実装機能の実行停止 |
| 4 | 検証失敗 |
| 5 | 本体導入・更新・削除またはセットアップ失敗 |
| 6 | 復旧経路未確認 |
| 10 | 再起動が必要 |

再起動が必要な場合でも処理自体が成功しているときは、レポートに成功状態を記録した上で終了コード`10`を返す。

#### 終了条件との対応

| 条件 | 終了区分 |
|---|---|
| 初回構成の対話不能・選択未完了、または対話不能な環境で必須確認が必要 | 安全確認失敗 |
| 変更操作に必要なroot権限がない | 引数または設定エラー |

区分に対応する数値は[終了コード](#終了コード)を参照する。確認の要否は[構成選択](POLICIES.md#構成選択と継続管理)と[対話確認](POLICIES.md#対話確認と省略)、必要権限は[権限モデル](SECURITY_POLICY.md#権限モデル)に従う。

#### 共通CLIの未確定契約

コマンドの役割、既存の入力・出力と変更可否を定めた部分と、次の未確定部分を区別する。[自動化入口のCLI契約](#自動化入口のcli契約)とは別に、共通CLIを使用する機能へ影響する。

| 対象 | 確定が必要な内容 |
|---|---|
| `status`・`verify` | 具体的な入力、検査項目と結果の集約、人間向け表示・コマンド別の`data`、停止・失敗と終了区分の対応 |
| `--config PATH` | パスの解釈・許容条件、未指定時の設定選択、指定先の欠損・不正時の扱いと検証順序 |
| `--log-level LEVEL` | CLIの受理値・未指定時動作と、[基本設定](#configyml)の`serverseed.log_level`の許容値・[既定値](POLICIES.md#基本設定の既定値)との対応、同時指定時の優先順位 |
| 構造化出力 | [共通JSON出力](#共通json出力)の`data`のコマンド別契約、`warnings`・`errors`の要素形式と、正常・停止・失敗時の出力・終了区分の対応のうち未定義の部分 |
| `support-bundle` | `--output PATH`未指定時の扱いと指定先の解釈、ファイル名の`MACHINEID`・`TIMESTAMP`の具体形式、収集範囲・件数・容量・時間の上限、収集失敗・中断時の成果物、tar.gzの保存と共通`--json`・`--dry-run`の対応 |

既存の状態名・終了コード・JSON例・設定の許容値と既定値は変更せず、これらだけで上記の契約を充足した扱いにしない。未確定値や対応を独断で補完せず、[仕様充足の判定](POLICIES.md#実装着手と仕様充足の判定)に従う。

共通入力・出力・集約・整形の審査用候補は[Phase 2・P02-CLI・B9](complete/PHASE_02.md#p02-cli)、応答の全子型と型付き境界は[CommandData](complete/PHASE_02.md#検査観測の固定集合)、マスター応答は[担当型](complete/PHASE_08.md#マスターcliの解析と応答全集合)を参照する。候補の記載は採用・既存契約の切替を意味しない。型/検査集合の採用、出力保全と外部方式の未達は[担当判断](complete/PHASE_02.md#未決事項と成立判定)へ対応付ける。

### 宣言型構成管理（内製IaC）

#### 宣言型構成管理の責務と適用範囲

本節は、[内製IaC方針](PRINCIPLES.md#内製iac)に基づくCoreの構成管理について、定義解析、実状態の取得、差分と計画、適用制御および結果検証の責務を定める。適用の許可・禁止は[宣言型構成管理の適用条件](POLICIES.md#宣言型構成管理の適用条件)を参照する。

初期の限定対象は、ServerSeedが管理するファイル・ディレクトリとその権限とする。パッケージ・systemdサービスの宣言型管理、その後の外部媒体・SSH経路との統合を段階的に扱う。段階ごとの実施先と進捗は[ロードマップ](ROADMAP.md)を参照する。この対応順序は宣言型管理の拡張順であり、既存のOS導入や構成固有機能の責務を削除・移管するものではない。

対象OS・CPUと事業者資源との境界は[製品の対応範囲](#対応範囲)、各構成が適用する機能は[構成の分離](POLICIES.md#構成の分離)に従う。OS導入、バックアップ、採掘監視およびアプリ固有の検証・復旧そのものを、ファイル資源の適用だけで代替しない。

#### 構成入力と状態の区分

次の三つを区別して処理へ渡す。本表は意味上の区分であり、新しい設定キー・JSONフィールド・保存形式を定義するものではない。

| 区分 | 処理で使用する情報 |
|---|---|
| 望ましい構成 | 選択済み構成に適用する定義と、確定した利用者入力から求める資源・属性の要求。形式と解析は[共通設定](#構成定義の解析)、収録定義は[組込み資材](#組込み資材)を参照 |
| 観測した実状態 | 識別した対象OSの資源から実際に取得した内容・属性、取得条件と確認不能事項。取得不能を資源の不在や要求との一致として扱わない |
| 適用記録 | 計画・操作に対応する実施内容と検証結果。過去の適用結果を、現在の実状態を観測した結果の代わりにしない |

対象機器、実行環境と対象OSの対応は[共通基盤](#実行環境と管理対象)へ照合する。共通の状態名と[状態スナップショット](#状態スナップショット)の意味は維持し、IaC用の別の総合状態や状態の正本を設けない。

#### 資源の識別と管理範囲

資源は、対象機器・対象OS、担当責務、資源種別と対象内の識別情報へ対応付ける。ファイル・ディレクトリでは配置先と管理する属性を特定し、同じパス名でもLive環境・マスター・SSH管理先を別の対象として区別する。

差分を求める前に、選択済み構成が管理する資源と属性、対象外の資源と属性、複数機能が共有する資源を識別する。ファイルシステム上に存在することや、親ディレクトリを管理することだけで、その配下全体を管理対象に取り込まない。所有範囲・競合による停止と、定義から外れた資源の扱いは[適用条件](POLICIES.md#宣言型構成管理の適用条件)に従う。

識別子の具体形式、管理範囲の表現、パスの検証と同一資源の判定は[未確定契約](#宣言型構成管理の未確定契約)とする。既存の設定項目や管理マーカーだけで、資源単位の管理範囲が確定したとは扱わない。

#### 宣言型構成管理の処理フロー

次の処理を既存の[ライフサイクル](#構成適用との接続)へ接続する。

1. 定義を解析し、対応する形式・版、型、必須項目と資源の管理範囲を照合する。解析契約は[構成定義の解析](#構成定義の解析)を参照する。
2. 対象OSから管理属性を観測し、望ましい構成・実状態・適用記録を区別して照合する。観測結果の欠損・取得不能は計画の停止理由へ対応付ける。
3. 管理対象の差分から、適用する資源・属性、処理順序、影響、前提条件、保全・復旧可能範囲を求め、[更新計画](#更新計画)へ対応付ける。競合・前提不足・未対応は実行不能理由として扱う。
4. 必須選択と計画確認を終えた変更操作で、[共通ロック](#ロックと同時実行)の下で対象、定義と観測した前提を再照合する。確認後の条件変化には更新計画の破棄・再検査・再確認を適用する。
5. 確定した差分だけを適用し、資源ごとの適用位置と結果を親の計画・操作へ対応付ける。ファイル置換は[原子性](#原子性と書き込み)、OSコマンドの呼び出しは[外部コマンド実行](#外部コマンド実行)の契約を使用する。
6. 実資源を再取得して要求と照合し、適用済み範囲、失敗・未確認と残作業を判別する。結果は[操作状態](#操作状態)と[実行履歴](#実行履歴)へ対応付け、構成全体の検証は各構成の担当仕様へ接続する。

計画作成と読み取り専用の差異検出では、[読み取り専用時の記録処理](#読み取り専用時の記録処理)を使用する。計画・資源別結果の具体形式と既存出力への対応は未確定であり、上記の流れだけで既存のJSON例に資源単位の情報を表現済みと扱わない。

#### 再適用と差異検出

再適用では、現在の実状態から管理属性の差分を再計算し、前回の計画や成功記録をそのまま再実行しない。一致する属性と変更が必要な属性を分け、[適用条件](POLICIES.md#宣言型構成管理の適用条件)の不要な書き換え・再起動の禁止へ照合する。比較・正規化と前提条件の同一性判定は[未確定契約](#宣言型構成管理の未確定契約)で管理する。

読み取り専用の検査で見つかった差異は、事実、影響と必要な操作候補として既存の[CLI出力](#共通json出力)へ対応付ける。差異の表示だけで変更工程へ移行せず、具体的な出力項目はCLI契約の確定時に定める。

#### 宣言型構成管理の中断と復旧

中断時は資源ごとの実適用位置、実状態と記録を親の計画・操作に照合し、適用済み・未適用・確認不能の範囲を識別する。再開・再投入には[憲章第11条](CHARTER.md#第11条-再開と工程通過)、総合状態の判定には[前回処理状態](#前回処理状態)を適用する。遠隔応答の欠損は[マスターの結果照合](master/specification.md#中断と結果照合)へ接続する。

復旧計画では、資源別に保全元、変更前後の状態、復元方法、検証方法と復旧できない範囲を対応付ける。適用の失敗と復旧の成否を分け、[ロールバックの制約](POLICIES.md#ロールバック)に照合する。本体置換専用のトランザクション形式を、任意資源の復旧形式として流用済みとは扱わない。

資源別の記録・保全・復旧の具体契約は下表の未確定事項とする。記録が不足する範囲を未適用と推測せず、照合不能な資源に依存する後続の変更を進めない。

## 情報管理

### 共通設定とデータ形式

#### 設定・記録のファイル形式

人が編集するServerSeedの構成定義はYAML形式とし、ファイル拡張子は`.yml`に統一する。外部ツールが指定する受け渡しファイル名は、[USBセットアップ](#外部媒体のセットアップ)など該当する外部契約に従う。

機械処理を主目的とするマニフェストおよび状態スナップショットはJSON形式とし、追記型の実行履歴およびイベントログは1行1JSONのJSONL形式とする。

YAMLの読み込み制約は[設定入力の安全条件](SECURITY_POLICY.md#設定入力の安全条件)に従う。

秘密情報の扱いは[セキュリティポリシー](SECURITY_POLICY.md#秘密情報)に従う。

#### 構成定義の解析

YAML・JSONの解析はCoreの共通処理とし、各設定・マニフェスト・記録の型と意味は担当仕様へ照合する。宣言型管理へ渡す情報の区分は[入力と状態](#構成入力と状態の区分)、資源の項目と管理範囲は[資源定義の未確定契約](#宣言型構成管理の未確定契約)を参照する。解析できたことを、適用可能性や権限の確認の代わりにしない。

対応するYAML・JSONの版と構文範囲、文字コード、文字列・数値・真偽値・nullの解釈、重複キー・複数文書・参照の扱い、入力サイズ・深さ・解析時間・メモリーの上限と、制限超過・不正入力時の出力は未確定とする。対応しない構文の扱いも契約として確定し、形式名だけで完全互換を保証しない。[設定入力の安全条件](SECURITY_POLICY.md#設定入力の安全条件)と、各担当仕様の未知項目・型不正時の扱いは維持する。

本節では新しい設定キー、資源定義ファイルや保存形式を追加しない。既存設定との接続・版・移行を含む解析契約と受入条件が確定するまで、依存する解析・適用処理を[実装着手可能](POLICIES.md#実装着手と仕様充足の判定)と判定しない。

具体化の審査用候補は[Phase 2・P02-PARSE・B9](complete/PHASE_02.md#p02-parse)を参照する。構文・値型・上限の算定・エラー位置と受入設計の案であり、本節の未確定部分を確定済みへ切り替えない。実使用量の測定・各スキーマと移行・採用承認の未達は[担当判断](complete/PHASE_02.md#未決事項と成立判定)へ対応付ける。

#### `config.yml`

`config.yml`はServerSeed全体の基本設定を定義する。

生成時期と既存設定の扱いは[初回導入の保護条件](POLICIES.md#初回導入の保護条件)に従う。以下は形式例であり、未指定時の値は[基本設定の既定値](POLICIES.md#基本設定の既定値)を参照する。

```yaml
serverseed:
  config_revision: 1
  environment: cloud
  profile: server
  log_level: info
  allow_reboot: false
  update_channel: stable
```

`environment`は導入経路を記録し、`usb`または`cloud`とする。ISOは媒体形式であり、独立した実行環境値にしない。ISOを外部媒体から起動して物理PCへ導入する経路は`usb`、マスターからSSHでCloud対象へ導入する経路は`cloud`とする。後者はOS導入の有無に依存せず、SSH用に仮想メディアを使用するだけで`usb`へ変えない。この値だけを根拠に、現在の実行環境を判定したりディスク操作を許可したりしない。

`config.yml`の必須項目は次とする。

| 項目 | 型 | 必須 |
|---|---|---|
| `serverseed.config_revision` | integer | はい |
| `serverseed.environment` | string | はい |
| `serverseed.profile` | string | はい |
| `serverseed.log_level` | string | いいえ |
| `serverseed.allow_reboot` | boolean | いいえ |
| `serverseed.update_channel` | string | いいえ |

`log_level`は`debug`、`info`、`warn`、`error`のいずれかとする。`update_channel`は初期実装では`stable`のみ有効とする。

`profile`は単一のstringとし、許容値と対応する構成は次のとおりとする。配列や複数値の連結文字列は受け付けない。値の確定・保存と管理マーカーとの照合は[初期構成選択と継続管理](POLICIES.md#構成選択と継続管理)に従う。

| 値 | 構成 |
|---|---|
| `master` | マスター管理構成 |
| `mining` | マイニング構成 |
| `server` | サーバ構成 |

未知のトップレベルキーは設定エラーとする。未知の下位キーは警告ではなく設定エラーとし、変更操作を開始しない。

#### `policy.yml`

`policy.yml`の項目と型は次のとおりとする。以下の値は形式例であり、既定値と許可条件は[共通ポリシーの既定値](POLICIES.md#共通ポリシーの既定値)を参照する。

```yaml
policy:
  require_backup_before_update: true
  require_ssh_recovery_path: true
  allow_password_auth_disable: true
  allow_unattended_security_updates: true
  allow_destructive_disk_setup: false
```

ディスク消去の許可条件は[ディスク操作](POLICIES.md#ディスク操作)を参照する。

`policy.yml`の必須項目は次とする。

| 項目 | 型 | 必須 |
|---|---|---|
| `policy.require_backup_before_update` | boolean | いいえ |
| `policy.require_ssh_recovery_path` | boolean | いいえ |
| `policy.allow_password_auth_disable` | boolean | いいえ |
| `policy.allow_unattended_security_updates` | boolean | いいえ |
| `policy.allow_destructive_disk_setup` | boolean | いいえ |

型が一致しない場合は設定エラーとする。

設定値の適用条件に残る未確定部分は、[バックアップ設定](POLICIES.md#バックアップ設定の未確定条件)と[セキュリティ設定](SECURITY_POLICY.md#セキュリティ設定の未確定条件)を参照する。型・既定値と、各操作の必須保護条件との対応を区別し、本節で許可・禁止の本文を複製しない。

#### 構成記録の互換性

`config.yml`と管理記録の対応は[共通基盤](#構成選択結果と管理記録)、内包機能の対応は[構成の分離](POLICIES.md#構成の分離)を参照する。既存の構成値の意味は維持し、マスター固有の設定形式は[担当仕様](master/specification.md#設定と管理情報)へ集約する。

[構成値](#configyml)の追加だけで、旧二択形式を扱う本体との読み書き互換性を保証しない。構成設定・管理記録・更新情報の版の扱い、構成リビジョンと互換範囲、旧形式からの移行・検証・切り戻しの詳細は未確定とする。既存例の版番号を、移行や新形式の受入検証が完了した根拠にしない。依存する実装は[仕様充足](POLICIES.md#実装着手と仕様充足の判定)を確認してから行う。

#### 本体導入と構成管理

本体と構成セットアップの関係は[本体導入](POLICIES.md#本体導入)、実行手順は[バイナリ導入](#バイナリ導入)を参照する。

本体の現在の導入情報は`/var/lib/serverseed/install.json`に保存する。

```json
{
  "schema_version": 1,
  "status": "installed",
  "serverseed_version": "0.1.0",
  "architecture": "amd64",
  "binary_sha256": "hex",
  "installed_at": "RFC3339"
}
```

`status`は`installed`または`removed`とする。`removed`は本体削除が正常終了したことを表し、バージョンとハッシュは削除した本体の情報を保持する。導入情報は現在状態の記録であり、追記型の履歴にはしない。

導入情報と管理情報は[状態判定の優先順位](#状態判定の優先順位)で対象OSを確認した後に評価する。管理マーカーのない対応OSは、本体導入済みでも`ADOPTABLE`とする。`installed`の記録と実ファイルが不一致、または本体変更操作が未完了なら`RECOVERABLE`とする。正常に本体を削除した未管理OSは`ADOPTABLE`であり、設定やログが残るだけで破損と判定しない。管理マーカーが残るOSは、導入情報にかかわらず管理対象として整合性を検査する。

#### 構成選択結果と管理記録

構成の選択・継続管理・変更の条件は[構成選択と継続管理](POLICIES.md#構成選択と継続管理)に従う。選択結果の形式は[共通設定](#configyml)と[管理マーカー](#管理マーカー)を参照する。

選択結果は一つの構成値として管理マーカーの`profile`、状態スナップショットの`serverseed.profile`、構成選択済みの実行履歴の`profile`へ対応付ける。マスターが内包する機能を理由に、記録ごとに別の構成値を保存しない。形式・版の互換性は[構成記録の互換性](#構成記録の互換性)、内包機能の検証は[マスター管理構成](master/specification.md#構成の検証)を参照する。

#### 共通状態判定

ServerSeedは対象ディスクまたは対象OSを検査し、次の状態に分類する。

| 状態 | 意味 |
|---|---|
| `EMPTY` | OSが存在しない |
| `ADOPTABLE` | 対応OSだが構成セットアップ未完了 |
| `MANAGED` | ServerSeed管理対象OS |
| `RECOVERABLE` | 導入・管理対象で、変更未完了、導入情報の不整合、正常起動または構成の問題がある |
| `UNKNOWN` | 未対応OS、判定不能または安全未確認 |

状態別の基本動作は[状態に応じた基本動作](POLICIES.md#状態に応じた基本動作)を参照する。

管理対象であることは、少なくとも次の情報を使用して判定する。

- OSおよびバージョン
- ルートファイルシステム
- `/etc/os-release`
- ServerSeed管理マーカー
- マシン識別情報
- ServerSeed構成バージョン
- 前回処理の完了状態

主要な管理情報の配置は[管理ファイル一覧](#管理ファイル一覧)を参照する。

単にOSらしいファイルが存在するだけでは、管理対象と判定しない。

#### 状態判定の優先順位

状態判定は安全側に倒すため、次の順に検査し、最初に該当した状態を採用する。

1. 対象ディスクまたは存在するルートファイルシステムを読み取れない場合は`UNKNOWN`とする。
2. 外部媒体またはSSH実行環境から識別した対象ディスクで、パーティション、OS、ブートローダーが存在せず、導入・構成管理の記録もないことを確認できる場合のみ`EMPTY`とする。実行環境の起動ディスクと混同しない。
3. それ以外の対象は[対応OSの判定](#ubuntu-2404-lts判定)を行う。未対応OS、OS情報の欠損・読み取り不能、または対応を確認できない場合は`UNKNOWN`とする。管理マーカーがあってもこの判定を省略しない。
4. [前回処理状態](#前回処理状態)が未完了、[本体導入情報](#本体導入と構成管理)が不整合・未完了、または構成管理の証跡がある対象で起動構成・必須管理ファイルの欠損・破損・不正、保存済み構成の不明・不正・不一致を検出した場合は`RECOVERABLE`とする。内包機能の必須項目も、[機能適用の範囲](POLICIES.md#構成の分離)に対応付けて検査する。
5. [管理マーカー](#管理マーカー)、マシン識別情報、構成バージョンおよび保存済み構成が整合する場合は`MANAGED`とする。
6. 管理マーカーがなく、[本体導入と構成管理](#本体導入と構成管理)の条件を満たす対応OSは`ADOPTABLE`とする。Cloud版では[導入の前提](#cloudの前提)も確認する。
7. 上記に該当しない場合は`UNKNOWN`とする。

構成管理の証跡は、検査対象の管理マーカー、またはその対象に構成を適用した操作記録を指す。本体だけの導入・正常削除の記録を構成管理の証跡と扱わず、構成未セットアップ時の管理マーカー・構成設定・構成固有ファイルの未作成だけで手順4へ該当させない。

`EMPTY`は内容の判定であり、ディスクへの書き込み許可ではない。OSが見つからないだけで空ディスクと推測せず、既存パーティションや管理記録がある場合は手順2を満たさない。Cloudの導入能力は[対象識別](#cloudの実行環境と対象os)、消去可否は[ディスク操作](POLICIES.md#ディスク操作)で別に判定する。

#### 管理マーカー

管理マーカーの検査には[状態判定の優先順位](#状態判定の優先順位)を適用する。`/etc/serverseed/managed`はJSON形式とし、少なくとも次を含める。

```json
{
  "managed": true,
  "machine_id": "string",
  "created_at": "RFC3339",
  "serverseed_version": "0.1.0",
  "config_revision": 1,
  "migration_revision": 0,
  "profile": "server"
}
```

`profile`は[`config.yml`](#configyml)の`serverseed.profile`と一致しなければならない。欠損、不正値または不一致の場合は`RECOVERABLE`とする。

`managed`が`true`でない場合、または`machine_id`が`/etc/serverseed/machine-id`と一致しない場合は`MANAGED`と判定しない。

#### 前回処理状態

前回処理の記録形式とプロセスの確認方法は[操作状態](#操作状態)を参照する。

前回処理が`running`、`interrupted`、または終了状態不明のまま残っている場合は`RECOVERABLE`とする。継続可否は[未完了操作](POLICIES.md#未完了操作)に従う。実行中の操作に属する診断は[トランザクション診断](#doctor)として区別し、新しい変更操作を並行開始しない。

#### 状態スナップショット

`/var/lib/serverseed/state.json`は現在の判定結果を保存する。ファイルは再生成可能なキャッシュとして扱い、判定の唯一の根拠にしてはならない。このキャッシュの生成・更新は、[CLIの変更可否](POLICIES.md#コマンド別の変更可否)に定める管理状態の変更に含める。

```json
{
  "schema_version": 1,
  "state": "MANAGED",
  "detected_at": "RFC3339",
  "machine_id": "string",
  "os": {
    "id": "ubuntu",
    "version_id": "24.04",
    "kernel": "string"
  },
  "boot": {
    "mode": "uefi",
    "secure_boot": "unknown"
  },
  "serverseed": {
    "installed": true,
    "profile": "server",
    "version": "0.1.0",
    "config_revision": 1,
    "migration_revision": 0
  },
  "checks": [
    {
      "id": "os.supported",
      "result": "pass",
      "message": "Ubuntu 24.04 LTS detected"
    }
  ]
}
```

`state`は[共通状態判定](#共通状態判定)の状態名を使用する。`checks[].result`は`pass`、`warn`、`fail`、`unknown`のいずれかとする。

構成未選択の場合、`serverseed.profile`、`config_revision`および`migration_revision`は`null`とし、未確定の値を生成しない。`serverseed.installed`は管理対象判定ではなく、検査対象OSの本体導入状態を表す。外部媒体・マスター・SSH一時環境上の実行本体を、対象OSへ導入済みと取り違えない。

生成・更新と照合の未確定部分は[共通管理記録](#共通管理記録の未確定契約)を参照する。

#### 操作状態

`/var/lib/serverseed/operation.json`は実行中または直近の変更操作を表す。

変更操作の開始時に実行中状態を記録し、成功または失敗の確定時に終了状態を記録する。

```json
{
  "schema_version": 1,
  "operation_id": "string",
  "command": "update",
  "status": "running",
  "started_at": "RFC3339",
  "finished_at": null,
  "pid": 1234,
  "plan_id": "string",
  "lock_path": "/var/lib/serverseed/lock"
}
```

`status`は`running`、`success`、`failed`、`interrupted`のいずれかとする。変更操作の開始時に`running`を記録できない場合、その操作を開始してはならない。

独立した本体変更操作では`command`を`self install`、`self update`、`self uninstall`のいずれかとし、構成未選択の実行履歴では`profile`を`null`にする。通常の`update`内では親の操作ID・ロックを引き継ぎ、親の`command`を上書きしない。初回は権限を確認して管理ディレクトリとロックを用意した後に操作状態を記録し、配置を開始する。

処理中にプロセスが終了し、`running`のまま残った場合、次回起動時にPIDの存在と開始時刻を確認する。実行中プロセスが確認できない場合は`interrupted`として扱う。

識別情報・プロセス照合と記録確定の未確定部分は[共通管理記録](#共通管理記録の未確定契約)を参照する。

#### 読み取り専用時の記録処理

[コマンド別の変更可否](POLICIES.md#コマンド別の変更可否)と[成果物の保存](POLICIES.md#成果物の保存)に従い、読み取り専用コマンド、`plan`および`--dry-run`では、検出した中断をメモリ上の判定として報告する。`operation.json`の書き戻し、状態キャッシュの生成・更新、実行履歴への追記、既定保存先への自動的なログ・レポート出力は行わず、初期化のための管理ディレクトリやロックファイルも作成しない。診断情報は標準出力または標準エラーへ出す。利用者が明示した成果物の保存だけは上記ポリシーの条件に従う。

中断記録の永続化や後始末は、変更を許可された復旧・変更操作が[共通ロック](#ロックと同時実行)の下で状態を再検査して行う。実行中の親操作に属する[トランザクション診断](#doctor)も記録を変更せず、親が保持するロック・操作IDを照合して読み取り専用の診断を行う。

#### ロックと同時実行

同時実行の許可、読み取り専用操作のロック取得条件、競合と解除の扱いは[変更操作の排他](POLICIES.md#変更操作の排他)を参照する。

変更操作は`/var/lib/serverseed/lock`を使用して排他制御する。本体変更と構成・OSの変更も同じロックを使用し、子処理へ分ける場合も検証と操作状態の確定までロックを維持する。

取得・所有確認・引き継ぎ等の未確定契約は[共通管理記録](#共通管理記録の未確定契約)を参照する。

#### 原子性と書き込み

管理ファイルの保全・確定条件は[憲章第6条](CHARTER.md#第6条-安全と保全)を適用する。ServerSeedが管理する設定、状態、履歴およびレポートを書き換える場合は、一時ファイルへ書き込み、同期し、同一ファイルシステム内のrenameで置き換える。利用者指定先への成果物保存は[CLIの成果物保存](POLICIES.md#成果物の保存)に従い、管理ファイルの置換とは区別する。本体置換の手順と中断時の扱いは[本体の置換と復旧](#本体の置換と復旧)に従う。

重要な管理ファイルの部分書き込み、空ファイル化、不完全なJSONまたはYAMLを残してはならない。管理ファイルの書き込み失敗時は失敗状態を記録し、次回起動時に`RECOVERABLE`として扱う。

追記型履歴との対応と、記録失敗・中断時の照合に残る未確定部分は[共通管理記録](#共通管理記録の未確定契約)を参照する。

#### 外部コマンド実行

データと実行の分離は[憲章第6条](CHARTER.md#第6条-安全と保全)に従い、外部コマンドは引数配列として実行し、シェル展開に依存しない。

外部コマンドの標準出力、標準エラー、終了コード、実行時間を記録する。記録先は[読み取り専用時の記録処理](#読み取り専用時の記録処理)に従って区別し、ログ出力時の秘匿化は[秘密情報の扱い](SECURITY_POLICY.md#秘密情報)に従う。

実行時間の制限は[憲章第6条](CHARTER.md#第6条-安全と保全)に従う。タイムアウト時は処理を失敗として記録し、後続の変更操作を停止する。

#### 外部コマンドの未確定契約

[外部コマンド実行](#外部コマンド実行)で定義済みの実行・記録条件と、次の未確定部分を区別する。

| 対象 | 確定が必要な内容 |

| 時間制限 | 操作ごとの指定元・型・単位・許容範囲、未指定時の値または算定式、計測の開始・終了、超過の判定と再試行の回数・待機条件 |
| 中断と終了確認 | 時間超過・キャンセル・親処理終了時の子プロセスを含む停止対象、停止方法・順序・待機上限、終了確認と残存・確認不能時の保全・照合、後続処理・排他・操作記録への接続 |
| 出力と結果 | 標準出力・標準エラーの取得量・メモリー上限と読取り完了、超過・取得失敗・途中出力の扱い、起動失敗・非ゼロ終了・シグナル・時間超過・中断の区別と呼出元の出力・終了区分への対応 |

具体値、停止方式、再試行方式や新しい終了コードを本表で確定しない。既存の[記録先の区分](#読み取り専用時の記録処理)と[秘匿化](SECURITY_POLICY.md#秘密情報)は維持し、未確定部分に依存する実装は[仕様充足の判定](POLICIES.md#実装着手と仕様充足の判定)へ照合する。

#### 実行履歴

`/var/lib/serverseed/history.jsonl`は1行1JSONとし、操作ごとに追記する。

各行は少なくとも次を含める。

```json
{
  "operation_id": "string",
  "command": "update",
  "started_at": "RFC3339",
  "finished_at": "RFC3339",
  "result": "success",
  "profile": "server",
  "serverseed_version_before": "0.1.0",
  "serverseed_version_after": "0.1.1"
}
```

履歴ファイルの書き込み成功を、すべての変更操作の成功条件とする。必須記録の未確定時には[憲章第8条](CHARTER.md#第8条-検証と事実の区別)を適用する。

追記・同期と他の管理記録との確定順序の未確定部分は[共通管理記録](#共通管理記録の未確定契約)を参照する。

#### ログ形式

ファイルへの記録を許可された操作のログは、人が読むテキストログと機械処理用JSONLを分けて保存する。読み取り専用操作の扱いは[読み取り専用時の記録処理](#読み取り専用時の記録処理)を参照する。

保存先は[共通設定の管理ファイル一覧](#管理ファイル一覧)を参照する。

ログの秘匿化は[秘密情報の扱い](SECURITY_POLICY.md#秘密情報)に従う。

具体的な記録形式と保持条件の未確定部分は[共通管理記録](#共通管理記録の未確定契約)を参照する。

## 継続性

### 本体の導入・更新・復旧

#### 実行側と対象側

導入・保守の利用者向け入口は[実行入口と通常運用](POLICIES.md#実行入口と通常運用)、実行環境と対象の識別は[憲章第6条](CHARTER.md#第6条-安全と保全)に従う。[本体の導入・更新・復旧](#本体の導入更新復旧)の取得・本体管理・更新は、その入口から確定した計画を適用する共通手順とし、独立した手動導入経路として案内しない。

| 実行側 | 共通処理への接続 |
|---|---|
| 外部媒体 | [USB手順](#外部媒体による導入と保守)で対象内蔵OSを識別し、対象OS内の処理とLive環境側の制御を分ける |
| マスター | [マスター管理](master/specification.md)が選択・計画・接続を制御し、[Cloud手順](#sshによるcloud環境の導入と保守)から対象側の共通処理を呼び出す |
| 対象OS | 本体配置、構成、サービス、状態・操作・履歴を自身の管理領域へ記録し、検証結果を実行側へ返す |

マスターや一時実行環境で`self`を実行しただけでは、対象OSへ本体を配置したことにならない。OS未導入時は対象OSの用意を[物理PC](#外部媒体のセットアップ)または[Cloud](#cloudへのosインストール)の手順で先に行う。

対象の操作状態・ロックを実行側へコピーして対象側の管理を代替しない。OS導入前・再起動中を含む制御側と対象側の操作ID・ロックの引き継ぎ、要求の重複防止と記録の保存・照合形式は未確定とし、[マスター制御契約](master/specification.md#未確定契約)または[媒体からの引き継ぎ](#外部媒体による更新バックアップ復旧)の確定を着手条件とする。

#### 構成適用との接続

構成の定義と実状態から変更を求める処理は[宣言型構成管理](#宣言型構成管理の処理フロー)を使用する。資源別の差分と前提条件を[更新計画](#更新計画)へ接続し、選択済み操作の適用・保全・復旧・総合検証の中で扱う。IaC専用の別系統の計画・確認や、独立した適用経路は新設しない。

`setup`・`update`・`recover`の各操作で許可された範囲と[宣言型管理の適用条件](POLICIES.md#宣言型構成管理の適用条件)を照合する。[本体だけの変更](POLICIES.md#本体更新の変更範囲)に構成適用を混在させず、本体置換専用の復旧を一般資源の復旧へ拡張しない。資源別の照合・復旧は[中断と復旧](#宣言型構成管理の中断と復旧)、対象間の引き継ぎは[実行側と対象側](#実行側と対象側)を参照する。

計画・資源別結果の具体形式と既存CLIへの対応は[未確定契約](#宣言型構成管理の未確定契約)として管理する。既存の計画例・終了コード・保存形式は変更せず、その例だけで新たな資源管理契約を充足した扱いにしない。

#### 初回の取得と配置

1. 対象OS、CPU、管理権限と実行時依存を確認する。入口側で確定したバージョンについて、[配布先](#成果物保管)からマニフェスト、署名および該当バイナリを権限を制限した作業領域へ取得する。ISOに収録した同じファイル一式や、検証済みの搬入物も使用できる。
2. [信頼鍵の初回導入と更新](SECURITY_POLICY.md#信頼鍵の初回導入と更新)と[署名およびチェックサム](SECURITY_POLICY.md#署名およびチェックサム)に従い、既存の`gpgv`と`sha256sum`で確認する。実行時依存が欠ける場合は不足項目を表示し、実行や本体配置を開始しない。
3. 検証済みバイナリを絶対パスで指定し、対象OS内で[selfコマンド](#self)の`install`を実行する。本体の`version --json`とマニフェストのバージョンが一致することを確認する。
4. root権限、配置先の所有権、競合する実行本体、空き容量、既存の導入情報と未完了操作を確認し、計画・確認を経て[本体の置換と復旧](#本体の置換と復旧)を実行する。
5. [管理対象サーバのディレクトリ](#管理対象のディレクトリ)と[権限](SECURITY_POLICY.md#ファイル権限)に従って配置し、必要な管理ディレクトリと共通ポリシーの初期値を用意する。初回の信頼済みキーリングは未配置の場合のみ登録する。
6. 配置した本体のバージョン・ハッシュと読み取り専用診断を確認し、[本体導入情報](#本体導入と構成管理)を確定する。設定未作成は構成セットアップ待ちとして入口側へ通知し、確認済みのセットアップ計画があれば次の工程へ進む。

初回導入時の変更範囲と設定保持は[初回導入の保護条件](POLICIES.md#初回導入の保護条件)を参照する。

#### 更新前検査

更新開始前に少なくとも次を確認する。

- 更新情報の署名
- ファイルのチェックサム
- 対象マシン、管理状態および保存済み構成の整合性
- 更新成果物が共通基盤または選択済み構成を対象としていること
- 現在と更新後のバージョン
- OS互換性
- ディスク空き容量
- パッケージ管理の正常性
- SSDまたはストレージ状態
- バックアップの最終成功状態
- 前回処理が完了していること
- SSHまたはコンソールによる復旧経路

検査結果による実行可否は[共通の安全条件](POLICIES.md#共通の安全条件)に従う。

マスター自身への更新では、[内包機能の検証](master/specification.md#構成の検証)と[同居時の運用条件](POLICIES.md#マスター管理構成の運用)も計画に照合する。SSH管理先への変更と、マスター自身への変更を同じ対象と扱わない。

#### 更新処理

1. 更新情報を取得して検証する。
2. 変更予定を事前検査する。
3. 現在の設定とバージョン情報を保存する。
4. 必要なデータバックアップを確認または実行する。
5. OSおよび対象アプリを更新する。
6. 必要な構成移行を実行する。
7. サービスを起動または再読み込みする。
8. ヘルスチェックおよび総合検証を行う。
9. 本体変更が計画されている場合は、[本体の置換と復旧](#本体の置換と復旧)を最後の変更ステップとして実行する。
10. 成功状態または失敗状態を記録する。
11. 再起動の要否を表示する。

処理中の失敗は[共通の安全条件](POLICIES.md#共通の安全条件)に従う。

#### 本体の置換と復旧

本体だけの更新で変更できる記録と構成互換性の条件は[本体更新の変更範囲](POLICIES.md#本体更新の変更範囲)に従う。

状態確定と必須記録の根本条件は[憲章第6条](CHARTER.md#第6条-安全と保全)と[第8条](CHARTER.md#第8条-検証と事実の区別)を適用し、本体変更では以下の同期・検証・記録へ対応付ける。

本体変更では、[共通ロック](#ロックと同時実行)の取得後に状態を再検査し、次の手順を使用する。

1. 対象OS・CPU、導入情報、署名、保存済み構成に対する互換範囲、必要容量、復旧経路を確認する。通常の導入・更新ではSemVerで現在より古い本体を拒否する。同一バージョンで異なるハッシュの成果物も拒否する。
2. `/var/lib/serverseed/self-transaction/`に候補のマニフェスト・署名・ビルドメタデータ、変更前の導入情報と本体のハッシュ、管理対象の場合はバージョン記録の退避を保存する。本体は配置先と同一ファイルシステムの`/usr/local/bin/.serverseed.new`へ排他的に取得・コピーし、同期後に署名付きハッシュと再照合する。既存の一時ファイルを無条件に上書きしない。
3. 候補の絶対パスで`version --json`を実行し、バージョン、アーキテクチャと互換性情報を照合する。正常版がある場合は、その本体、`/var/lib/serverseed/release/`に保持した検証情報および導入情報を`/var/lib/serverseed/previous/`へ保全する。検証情報が欠ける状態で正常版と推測しない。
4. トランザクションの`phase`を`prepared`として永続化し、[共通の原子性](#原子性と書き込み)に従うrenameで配置本体を置き換える。実行中ファイルへの上書き書き込みは行わない。置換後は`phase`を`replaced`として記録する。
5. 配置後の本体を絶対パスで起動し、`version --json`と[トランザクション診断](#doctor)を検査する。成功したら導入情報と、管理対象の管理マーカー・バージョン記録を更新する。現在版のマニフェスト・署名・ビルドメタデータは`/var/lib/serverseed/release/`へ保持し、次回の更新・復旧にも使用する。
6. `phase`を`verified`として同期し、操作状態と実行履歴を確定してから一時領域を清掃する。記録失敗を含めてすべて成功するまで、ロックを解放せず成功を返さない。

トランザクションの記録は同ディレクトリの`state.json`とし、`schema_version: 1`、`operation_id`、`command`、`phase`、`before_sha256`、`after_sha256`、`staged_path`および`previous_path`を含める。初回の変更前ハッシュ・退避先は`null`とする。パスは上記の生成先に限定し、外部入力のパスを復旧時の書き込み先にしない。

配置後の検証に失敗した場合は、事前計画で許可された範囲で次の復旧手順を直ちに試み、元の操作は失敗として返す。復旧完了前に別の通常変更へ進まない。単なるSSH切断・結果未着は配置後検証の失敗と同一視せず、[中断と結果照合](master/specification.md#中断と結果照合)を先に行う。

中断後の`recover --self`は、署名付き候補・退避本体、導入情報、実配置ハッシュとトランザクションを照合する。配置が候補と一致し診断に成功する場合は記録を完了できる。それ以外は署名と現在の設定に対する互換性を確認した正常版へ戻し、元の操作は失敗または中断として記録する。rename直後で`prepared`のままでも、実配置ハッシュから処理位置を確認する。

初回導入に退避本体がない場合は、記録に一致する候補での導入完了、または今回新規配置した本体だけの除去を計画として提示する。対象を特定できない場合、署名を検証できない場合、または旧版が移行後の設定を扱えない場合は変更せず停止し、管理者の復旧を要求する。無関係な設定・データを巻き戻して本体だけの復旧を成功させない。

`self uninstall`は候補の取得・置換・起動検査を行わない。導入情報と現在版の署名付き検証情報を照合し、退避して`prepared`を記録した後に配置本体だけを除去する。除去後を`replaced`とし、実ファイルが存在せず保護対象が保持されていることを検査して導入情報を`removed`へ更新する。`after_sha256`と`staged_path`は`null`とし、最後に`verified`・操作結果を確定する。中断時はこの組み合わせを識別し、削除完了の確定か退避版の復元を計画する。配置対象が別ファイルへ変わっていた場合は削除しない。

#### 更新計画

`update`、`setup`、`recover`および`self`の変更操作は、変更開始前に計画を作成する。計画は人間向けに表示し、`--json`では構造化して出力する。

```json
{
  "schema_version": 1,
  "plan_id": "string",
  "command": "update",
  "created_at": "RFC3339",
  "target_state": "MANAGED",
  "requires_confirmation": true,
  "requires_reboot": false,
  "steps": [
    {
      "id": "backup.check",
      "title": "Check last backup",
      "destructive": false,
      "requires_network": false
    }
  ],
  "blocked_by": []
}
```

`blocked_by`が空でない計画は実行してはならない。計画作成のみを行う場合の変更可否と成果物の保存は[CLIのplan](#plan)に従う。

本体変更の計画には、取得元、固定したバージョン、候補ハッシュ、現在と変更後の配置、必要容量、既存設定への影響、退避先および復旧可否を含める。確認後に取得内容や前提条件が変わった場合は計画を破棄し、再検査・再確認する。

OS導入、独立バックアップおよびマスター制御の計画に必要な追加入力・出力形式は、[Cloud](#cloudの未確定契約)、[バックアップ](#バックアップの未確定契約)、[マスター](master/specification.md#未確定契約)の契約確定時に[更新計画](#更新計画)へ対応付ける。上記の既存JSON例に未定義の値を埋めて、遠隔実行や新しい操作を表現済みと扱わない。

計画の識別と操作記録への対応に残る未確定部分は[共通管理記録](#共通管理記録の未確定契約)を参照する。

#### 計画時と実行時の検証

本体の導入・更新を対象とする`plan`と`--dry-run`では、マニフェストの署名、参照するビルドメタデータのハッシュ・内容、固定した候補情報とローカルの前提条件を検査する。HTTPSのメタデータはメモリ上で処理し、本体の取得・配置・起動、一時ファイルや管理ディレクトリの作成は行わない。本体削除の計画は保存済み導入情報と現在版の検証情報を対象とし、新しい候補を取得しない。

計画だけの検査で未実施の本体ハッシュ照合・起動診断を検証済みと表示しない。未実施の範囲と実行時に必要な検証を、人間向けの要約と[共通JSON出力](#共通json出力)の`warnings`で示す。署名不正、メタデータ不一致、ローカル前提の不成立など、その段階で検出した問題は計画の`blocked_by`へ含める。

実行を要求された導入・更新では、取得を伴う準備も所定の計画・確認の範囲内で行い、[署名およびチェックサム](SECURITY_POLICY.md#署名およびチェックサム)と[本体の置換と復旧](#本体の置換と復旧)に従って候補の本体ハッシュ・バージョン・互換性を検証する。その結果を適用用の計画へ反映し、検証がすべて成功した場合だけ適用へ進む。準備の結果、確認済みの候補・変更内容・前提条件に差異が生じた場合は、[更新計画](#更新計画)に従って計画を破棄し、再検査・再確認する。計画だけの検査結果を、取得後の検証や適用の確認の代わりにしない。

#### 製品バージョンの管理

ServerSeed本体、構成定義、マイグレーションにはそれぞれバージョンを持たせる。

バージョン形式はSemantic Versioningを基本とする。ただし、構成定義とマイグレーションは互換性判定のために独立した整数リビジョンを併用できる。

管理対象サーバには、少なくとも次を記録する。

```text
serverseed_version
config_revision
migration_revision
last_successful_operation
last_successful_operation_at
```

#### 更新マニフェスト

更新マニフェストはJSON形式とし、署名対象に含める。

```json
{
  "schema_version": 2,
  "serverseed_version": "0.1.0",
  "config_revision": 1,
  "migration_revision": 0,
  "target_profiles": ["master", "server", "mining"],
  "target_os": {
    "id": "ubuntu",
    "version_id": "24.04",
    "lts": true
  },
  "build_metadata": {
    "path": "serverseed_0.1.0_build.json",
    "sha256": "hex"
  },
  "artifacts": [
    {
      "name": "serverseed",
      "type": "binary",
      "architecture": "amd64",
      "target": "x86_64-unknown-linux-gnu",
      "path": "serverseed_0.1.0_linux_amd64",
      "sha256": "hex",
      "size": 123456,
      "runtime_dependencies": ["libc.so.6", "ld-linux-x86-64.so.2"],
      "compatible_config_revision": {"min": 1, "max": 1},
      "compatible_migration_revision": {"min": 0, "max": 0}
    }
  ]
}
```

`target_profiles`は適用可能な構成の配列とし、各要素の許容値は[基本設定の構成値](#configyml)に従う。共通本体は検証済みの対象構成を列挙し、構成固有の成果物はその適用先だけを宣言する。保存済み構成が配列に含まれない、または対象構成を検証できない場合は適用しない。

マスター管理構成への適用には`master`の明示を必要とし、内包機能の構成値が併記されているだけでは代用しない。同居する機能の定義・互換性・受入条件を確認してから宣言し、機能の包含だけで適用対象を拡張しない。旧マニフェストの扱いを含む形式・版の移行は[構成記録の互換性](#構成記録の互換性)へ対応付け、欠損時に対象を推測しない。

`artifacts`には配布する各アーキテクチャの本体を一件ずつ記載する。上の例は一件を抜粋した形式例であり、`hex`とサイズは実配布値へ置き換える。`type`は`binary`、`architecture`と`target`の対応は[ビルドターゲット](#配布バイナリのターゲットとリンク)に従う。未対応CPU、重複候補、欠損フィールド、未知の型、サイズ・ハッシュの不一致を拒否する。

`path`は配布基点からの相対ファイル名とし、`[A-Za-z0-9][A-Za-z0-9._-]*`に一致する値だけを受け入れる。絶対パス、URL、親ディレクトリ参照、区切り文字、制御文字を含めない。`size`は正の整数バイト数、実配布の`sha256`は64桁の小文字16進数とする。`runtime_dependencies`は必要な共有ライブラリとローダーを列挙する。ABIの詳細は[ビルドメタデータ](#本体ビルドメタデータ)で固定し、`build_metadata`のハッシュで検証した後に導入先と照合する。この参照が欠ける場合も停止する。

互換範囲は整数の`min`以上`max`以下を表し、`min > max`は不正とする。構成未選択では現在の構成リビジョンを推測せず、OS・CPU・実行時依存と共通基盤への適用条件だけを検査する。本体の自己申告との照合は[version](#version)を使用する。

本体マニフェストはISOへ収録するため、ISO自身のハッシュを含めない。ISOのハッシュと収録本体との対応は[媒体マニフェスト](#媒体マニフェスト)に置き、循環参照を作らない。

マニフェストに未対応の`schema_version`、Ubuntu 24.04 LTS以外の対象バージョン、現在状態から移行不能なリビジョンが含まれる場合は更新しない。初期実装は本体用の版`2`だけを受け入れ、旧deb形式を自動変換しない。

### バックアップとデータ保護

実行条件とデータ保護は[バックアップとデータ保護](POLICIES.md#バックアップとデータ保護)を参照する。

#### バックアップの実行と保存先

バックアップは独立して選択できる保守操作と、更新計画内の保護工程を区別する。前者を更新の開始条件に置き換えず、後者は更新と同じ対象・計画・操作に対応付ける。利用者の入口は[実行入口](POLICIES.md#実行入口と通常運用)、選択は[必須選択と自動実行](POLICIES.md#必須選択と自動実行)に従う。

| 区分 | 担当 |
|---|---|
| 外部媒体側 | 内蔵OSとデータ、書き込み可能な保存先を識別し、選択済みバックアップを制御する。Live環境自身のデータを対象データとして採取しない |
| マスター側 | Cloud対象と操作・保存先の選択、SSH制御、結果の照合。接続したことだけでデータをマスターへ保存済みと扱わない |
| 対象側 | 対象の構成に合う方法でデータを整合した状態で取得し、保存・検証結果を返す。対象自身の管理記録へ対応付ける |
| 保存先 | 起動媒体・管理側・対象データとは別に、位置・機器識別・書き込み能力・容量・保全条件を確認する |

保存先を外部媒体・内蔵ディスク・マスターのいずれかへ自動的に決めず、[保存の禁止条件](POLICIES.md#バックアップとデータ保護)に照合する。

#### バックアップ状態

バックアップ状態はServerSeedが直接作成したもの、またはアプリ定義で指定された確認コマンドの結果から判定する。

バックアップ成功状態は少なくとも次を含める。

```json
{
  "schema_version": 1,
  "app": "example",
  "last_success_at": "RFC3339",
  "method": "command",
  "location": "string",
  "verified": true
}
```

更新前提としての判定は[バックアップの成功条件](POLICIES.md#バックアップの成功条件)に従う。

#### バックアップの復元確認

復元確認の方法、定期実施と重要更新の停止条件は[復元確認](POLICIES.md#復元確認)を参照する。

復元元の検証、対象OS・構成・データ種別と復元先の照合を計画へ含める。実行場所と対象場所を取り違えず、OS再導入とデータ復元を一つの無確認操作にしない。

#### バックアップの未確定契約

独立バックアップ・復元のCLI、保存先の形式・対応方式・選択入力、暗号化・鍵の保全、保持・削除、保存形式の版と互換性、転送中断・容量不足・破損時の扱い、Live環境と稼働OSそれぞれの整合性取得方式、復元手順・確認方法と有効期限は未確定とする。

マスター固有の保全範囲・復元契約とその未確定事項は[管理情報の保全と復元](master/specification.md#管理情報の保全と復元)を参照する。上記のバックアップ状態の形式例だけではこれらの操作契約を充足しない。着手可否は[仕様充足の判定](POLICIES.md#実装着手と仕様充足の判定)に従う。

## 提供と保守

### CI/CD

実行基盤と責任分担は[CI/CD](PRINCIPLES.md#cicd)、リポジトリ運用は[AGENTS.md](../AGENTS.md)を参照する。

実行の許可条件は[CIとリリースの実行許可](POLICIES.md#ciとリリースの実行許可)を参照する。

workflowごとの処理は次の定義に従う。

初期workflowは次とする。

| workflow | トリガー | 目的 |
|---|---|---|
| `ci.yml` | pull request、`main`へのpush | 通常CI |
| `release.yml` | `v*`タグ、手動実行 | リリース成果物作成 |
| `vm-test.yml` | 手動実行のみ | VMを使う破壊的操作の検証 |

`vm-test.yml`は通常CIの必須条件に含めない。VM試験の隔離条件は[CIの隔離](SECURITY_POLICY.md#ciの隔離)を参照する。

正式公開の検証条件は[公開前の検証](SECURITY_POLICY.md#公開前の検証)を参照する。

初期CIで必須とするジョブは次のとおりとする。

| ジョブ | 内容 |
|---|---|
| `format` | `cargo fmt --all -- --check`およびMarkdown整形確認 |
| `lint` | `cargo clippy --all-targets --locked -- -D warnings`、危険な外部コマンド実行と[依存関係](#依存関係の検査)の検査 |
| `test-unit` | `cargo test --lib --locked`によるunit test |
| `test-integration` | `cargo test --tests --locked`によるUbuntu 24.04 LTS上のCLI契約と、使い捨てコンテナ内での本体管理の検査 |
| `build` | `cargo build --release --locked --target TARGET`による`serverseed`バイナリ作成。`TARGET`は[配布ターゲット](#配布バイナリのターゲットとリンク)に従う |
| `package-iso` | 検証済みビルド成果物を使うUSB用ISOの作成と内容検査 |
| `spec-check` | [仕様充足](#仕様充足の検査)、[文書索引の製品仕様](DOCUMENT_INDEX.md#製品仕様)と実装上の固定値の矛盾、[受入条件とテストの対応](#仕様とテストの対応)の検査 |
| `cli-contract` | サブコマンド、共通オプション、JSON出力契約の検査 |

実行環境での禁止操作は[CIの隔離](SECURITY_POLICY.md#ciの隔離)を参照する。

ServerSeedのCIは、GitHub workflowから少なくとも次のローカルスクリプトを呼び出せるようにする。

```bash
ci/run-format
ci/run-lint
ci/run-unit
ci/run-integration
ci/run-build
ci/run-package
ci/run-spec-check
ci/run-cli-contract
ci/run-all
```

各CIコマンドはローカル開発環境でも実行できるようにし、workflowから共通利用する。

#### GitHubの役割

基盤の適用範囲は[現行の運用基盤](POLICIES.md#現行の運用基盤)に従う。本節で定義するGitHubのCI/CD上の役割は次のとおりとする。報告の受付条件は[報告ポリシー](POLICIES.md#報告の受付)を参照する。

- CI/CD workflowの起動
- CI結果の表示
- リリースタグ管理
- [配布先](#成果物保管)へのリリース成果物と検証情報の公開

GitHub Actionsを使用する場合、workflowは`.github/workflows/`に配置する。重複を避けるため、必要に応じて`ci/`および`release/`配下の補助スクリプトを呼び出す。

将来の基盤へ移行する場合は、[移行条件](POLICIES.md#運用基盤の移行条件)に従ってworkflow・スクリプトと成果物の対応を見直す。本節は切替済みであることを示さない。

#### CI実行環境

CIの標準実行環境はUbuntu 24.04 LTSコンテナまたはUbuntu 24.04 LTS仮想マシンとする。

CI実行環境には、[Rustツールチェーン方針](#rustツールチェーン)に従うコンパイラー・Cargo・rustfmt・Clippy、[ISO生成](#isoの作成)のツールおよび署名検証ツールを事前に導入する。ビルドターゲットに必要な標準ライブラリ、リンカーおよびシステムライブラリもCI用イメージに含める。

環境変更の条件は[CI環境の変更](SECURITY_POLICY.md#ci環境の変更)に従う。

CI用イメージは、再現可能な定義ファイルから作成する。イメージ定義はリポジトリ内で管理する。

#### 配布バイナリのターゲットとリンク

初期のRustビルドターゲットは、[対応アーキテクチャ](#対応アーキテクチャ)に対応する次のGNUターゲットとする。

| 配布アーキテクチャ | Rustターゲット |
|---|---|
| `amd64` | `x86_64-unknown-linux-gnu` |
| `arm64` | `aarch64-unknown-linux-gnu` |

リンク方式、必要な共有ライブラリおよびローダーを確認し、[成果物のビルドメタデータ](#本体ビルドメタデータ)に記録する。完全な静的リンクや実行時依存がないことを、未検証のまま保証してはならない。

検証範囲の区別は[憲章第8条](CHARTER.md#第8条-検証と事実の区別)を適用し、各ターゲットのバイナリは、対応アーキテクチャのUbuntu 24.04 LTS上で実行を検証する。

#### リリース

リリースはGit tagで管理する。タグ形式は`vMAJOR.MINOR.PATCH`とする。

管理者がリリース操作を実行した場合、CDは次を生成する。

- Linux amd64用`serverseed`バイナリ
- Linux arm64用`serverseed`バイナリ
- USB起動用amd64 ISO
- USB起動用arm64 ISO
- 本体用と媒体用のマニフェスト
- 本体ビルドメタデータ
- SHA-256チェックサム
- OpenPGP detached signature

公開対象の選定は[公開前の検証](SECURITY_POLICY.md#公開前の検証)に従う。

リリース成果物名は次を基本とする。

```text
serverseed_VERSION_linux_amd64
serverseed_VERSION_linux_arm64
serverseed_VERSION_usb_amd64.iso
serverseed_VERSION_usb_arm64.iso
serverseed_VERSION_build.json
serverseed_VERSION_manifest.json
serverseed_VERSION_manifest.json.asc
serverseed_VERSION_media.json
serverseed_VERSION_media.json.asc
serverseed_VERSION_checksums.txt
serverseed_VERSION_checksums.txt.asc
```

`VERSION`はGit tagの先頭`v`を除いたSemantic Versioning値とする。例として、タグ`v0.1.0`の場合は`serverseed_0.1.0_linux_amd64`とする。

リリース操作は、少なくとも次のコマンドで実行できるようにする。

```bash
release/build
release/build-iso
release/sign
release/verify
release/publish
```

`release/publish`の許可条件も[公開前の検証](SECURITY_POLICY.md#公開前の検証)に従う。

#### リリース工程

1. 固定タグ・コミットから両アーキテクチャの本体を一度だけビルドし、[受入条件](#配布導入の受入条件)を検証する。
2. 本体のビルドメタデータと[更新マニフェスト](#更新マニフェスト)を確定し、本番鍵でマニフェストへ署名する。これ以降、本体・メタデータ・マニフェストを変更しない。
3. `release/build-iso`に固定版の本体と署名付き情報を渡す。既存リリースから取得する場合も同じ検証を行う。ISO内のバイナリと候補バイナリをハッシュで照合し、別ビルドに置き換えない。
4. [ISOの作成](#isoの作成)と手動VM試験を完了し、生成したISOの情報を[媒体マニフェスト](#媒体マニフェスト)に記載して署名する。
5. 全配布ファイルのSHA-256一覧を作成し、一覧にも署名する。一覧自身とその署名は一覧の対象外とする。`release/verify`で相互参照とすべての必要な成果物を検査する。
6. 検証済み一式を非公開のdraft releaseへ配置し、取得後の再照合に成功した場合のみ同一タグの正式リリースとして公開する。部分失敗、成果物不足、ハッシュ変更がある場合は公開しない。

公開後の扱いは[公開物の固定](POLICIES.md#公開物の固定)を参照する。

#### 署名鍵の参照

鍵の分離・保管・利用は[リリース署名鍵](SECURITY_POLICY.md#リリース署名鍵)を参照する。

#### アーティファクト検査

本体の導入・更新・削除は、少なくとも次を検査する。

- [配置と権限](#初回の取得と配置)が正しく、設定・状態・ログが保護されること
- 構成未選択のまま本体だけを導入でき、`doctor --json`がその状態を区別すること
- 再導入、署名不正、競合配置、中断および復旧を[受入条件](#配布導入の受入条件)どおり扱うこと

生成したバイナリは、少なくとも次を検査する。

- `serverseed version`が成功すること
- `serverseed inspect --json`がJSONのみを標準出力へ出すこと
- `serverseed --help`が成功すること
- `serverseed doctor --json`がJSONのみを標準出力へ出すこと
- `serverseed plan update --json`が変更なしで計画またはブロック理由を出すこと

実行環境は[配布バイナリのターゲットとリンク](#配布バイナリのターゲットとリンク)、実行時依存の照合は[本体ビルドメタデータ](#本体ビルドメタデータ)に従う。新しいUbuntu環境で、RustやCargoを導入せず配布本体を実行できることも確認する。

ISOは[媒体マニフェスト](#媒体マニフェスト)の収録版・ハッシュと[起動互換性](#isoの起動互換性)を検査する。生成成功だけで合格にせず、構成選択前の非破壊性とUSB・仮想メディア双方の起動を確認する。

#### 成果物保管

CI成果物は一時保管とし、リリース成果物と区別する。

リリース成果物の公開先はGitHub Releasesとする。成果物のチェックサム、署名、ビルドメタデータを併せて公開する。別の公開先を設ける可否と搬入経路の扱いは[現行の運用基盤](POLICIES.md#現行の運用基盤)に従う。

既定の取得先と搬入経路の条件は[更新元](POLICIES.md#更新元)を参照する。

成果物には、ビルド元commit、タグ、ビルド日時、ビルド環境識別子、チェックサム、署名情報を紐づける。

#### 本体ビルドメタデータ

`serverseed_VERSION_build.json`は次の形式とする。値は形式例であり、実際の採用版・ビルド結果へ置き換える。

```json
{
  "schema_version": 1,
  "serverseed_version": "0.1.0",
  "tag": "v0.1.0",
  "commit": "commit-sha",
  "built_at": "RFC3339",
  "rustc_version": "adopted-version",
  "cargo_version": "adopted-version",
  "cargo_lock_sha256": "hex",
  "artifacts": [
    {
      "architecture": "amd64",
      "target": "x86_64-unknown-linux-gnu",
      "build_environment": "image-digest",
      "link_mode": "dynamic",
      "elf_interpreter": "/lib64/ld-linux-x86-64.so.2",
      "libraries": [
        {"soname": "libc.so.6", "required_versions": ["GLIBC_2.39"]}
      ],
      "linked_crates": []
    }
  ]
}
```

アーキテクチャごとに一件を記載し、版・タグ・コミットを本体用マニフェストとビルド対象へ照合する。`link_mode`は`static`または`dynamic`、静的リンク時の`elf_interpreter`は`null`とする。`libraries`は実際のELF依存と要求するABIの集合を記録し、`linked_crates`は組み込んだcrate名・バージョンを持つオブジェクトの配列とする。依存を推測で省略しない。標準ライブラリは上位のツールチェーン情報で、内製crateは`linked_crates`で識別し、[依存条件](POLICIES.md#rustと内製crateの依存条件)と[例外一覧](DEPENDENCY_EXCEPTIONS.md#外部依存の例外一覧)への適合を確認する。

導入時は必要なローダー・ライブラリ・要求ABIをすべて照合する。条件を判定できない場合は実行可能と扱わない。本体用マニフェストの署名と、このファイルへのSHA-256参照で真正性を確認し、未検証のメタデータで依存確認を省略しない。

#### 端末側への適用

端末側への適用責任は[CI/CD](PRINCIPLES.md#cicd)、入口は[導入・通常運用の区分](POLICIES.md#実行入口と通常運用)、自動更新の許可条件は[マイニングの自動更新と再起動](POLICIES.md#マイニングの自動更新と再起動)を参照する。マスターのSSH自動処理は製品の運用機能であり、[CI/CDからの自動デプロイ禁止](POLICIES.md#端末への自動デプロイ)とは区別する。

### 仕様充足の検査

`spec-check`は、文書索引、対象機能と使用する共通契約のファイル・節、[完全仕様の必須条件](POLICIES.md#完全仕様の必須条件)との対応、受入検証の設計、実装変更がある場合は変更ファイルとテストの対応を入力とする。

1. 全文書の相対リンク・節アンカーと文書索引の網羅性を確認し、同じ定義の重複・参照切れを検出する。
2. 対象範囲の各確認項目を正本へ対応付け、欠落、未確定、矛盾、理由のない適用外、例示だけの定義を抽出する。曖昧な表現は文脈と参照先を含めて確認し、単語の有無だけで充足と判定しない。
3. 対象外とした未確定事項への依存がないことを確認し、[実装着手と仕様充足の判定](POLICIES.md#実装着手と仕様充足の判定)に照合する。依存する例外は[依存関係の検査](#依存関係の検査)へ対応付ける。
4. 受入条件ごとの前提・入力・期待結果と検証方法を確認する。実装変更がある場合は[仕様とテストの対応](#仕様とテストの対応)で実装・テストの漏れを検査する。
5. 結果には対象コミットと対象範囲、正本のファイル・節、確認項目、充足・未達・適用外の判定と根拠、承認対象との対応を含める。

自動検査だけで判断できない項目は確認待ちとして残し、根拠のない成功にしない。実装対象の未達・確認待ちは検査失敗とする。文書だけの変更では未達事項を明示できるが、実装着手可能の判定には転用しない。

検査自体の受入条件は、必要項目が揃う対象の成功、項目欠落・不正な適用外・切れた参照・矛盾・未確定依存・期待結果やテストの欠落の検出とする。未達事項を含む文書変更の成功と、未達対象の実装変更の失敗を区別できることも確認する。検査の実装状況は[ロードマップ](ROADMAP.md)を参照する。

### 依存関係の検査

`lint`では[憲章第7条](CHARTER.md#第7条-提供元依存権利)と[依存条件](POLICIES.md#rustと内製crateの依存条件)への適合を、次の入力と判定で検査する。変更時の実施手順は[作業ルール](../AGENTS.md#rustと内製crateの依存制約)を参照する。

1. ルートと全内製crateのCargo manifestを構造化して読み、通常・開発・ビルド・workspace・ターゲット別・任意・条件付きの全依存宣言を列挙する。featureの既定値や現在のホストで有効な依存だけに絞らない。
2. 各path依存を正規化し、シンボリックリンク解決後もリポジトリ内にあることを確認する。registry・Git参照、第三者コードの持込み、リポジトリ外の実体を検出する。ローカルパスや`source: null`だけを内製の証明にしない。
3. `Cargo.lock`と`cargo metadata --format-version 1 --locked`の構造を照合し、依存グラフ、版、manifestの実体、所有責務を確認する。無効化済み・他CPU向けの宣言は手順1でも検査し、metadataの有効グラフだけで判定しない。lockfileに残った禁止依存も検出する。
4. `build.rs`、マクロ、生成コード、リンカー指定、FFI、vendor資材およびダウンロード処理を確認し、manifest外から禁止依存が入らないことを検査する。許可された[OS実行時依存](#本体ビルドメタデータ)と任意のアプリケーションライブラリを区別する。
5. 外部プログラム・Action・CIイメージ・ISO資材を[例外台帳](DEPENDENCY_EXCEPTIONS.md)のIDと対応付け、対象・現在状態・個別採用情報を[例外の使用条件](POLICIES.md#外部依存例外の使用条件)へ照合する。対象の漏れ、ID重複、未確定項目のある使用可能判定、承認用途・固定参照・ライセンス・ハッシュ・署名・検証結果との不一致を検出する。

不一致・未選定・未確認は検査失敗として、対象宣言または資材、正本の制約、停止理由を報告する。自動削除、依存の自動追加、lockfileの自動更新で合わせない。結果はビルド元コミットと検査環境へ紐づけ、リリース工程でも同じ対象を検査する。未実装の検査を合格扱いにしない。

### テスト体系

テストは次の階層で実施する。

| 種別 | 対象 |
|---|---|
| unit | 状態判定、設定読み込み、マニフェスト検証、更新計画 |
| integration | Ubuntu 24.04 LTSコンテナ上でのCLI、隔離した使い捨て環境での本体導入・更新・削除、読み取り専用検査 |
| vm | ディスク、ブート、復旧、破壊的操作を含む検証 |
| fixture | `/etc/os-release`、lsblk、systemctlなどの実行結果サンプル |

unit testは対象モジュール内の`#[cfg(test)]`で定義し、integration testの入口は`tests/*.rs`に配置する。fixtureは`tests/fixtures/`に保存する。実行コマンドは[CIジョブ](#cicd)に従う。

構成選択に既定値がないこと、`--yes`・cloud-initが初回選択を代行しないこと、保存構成の継承、不整合時の停止、[選択構成に対応する機能](POLICIES.md#構成の分離)だけを適用することをunit・integrationで検証する。マイニングの採掘停止、通信断、温度異常および更新失敗はfixture・模擬サービスで検証し、実採掘の制約は[検証環境の制約](SECURITY_POLICY.md#検証環境の制約)に従う。GPU・BIOS・復電起動は別の実機検証として結果を記録する。

テスト階層の適用条件と危険操作の隔離は[検証環境の制約](SECURITY_POLICY.md#検証環境の制約)に従う。

実機検証とVM専用規定の適用境界の確認先は、[検証環境の未確定条件](SECURITY_POLICY.md#検証環境の未確定条件)とする。本節の検証要求の記載を、試験の実施条件が確定した根拠にしない。

#### 状態判定と非変更操作の受入条件

下表の前提と検証対象をunit・integrationのケースへ対応付ける。期待する判定・副作用・停止条件は参照先の正本から照合し、表内で別定義しない。USB固有の状態はfixtureまたはテスト用ディスクイメージで再現し、危険操作は[検証環境の制約](SECURITY_POLICY.md#検証環境の制約)に従って隔離する。

#### 仕様とテストの対応

[仕様駆動型開発](../AGENTS.md#仕様駆動型開発)の追跡は、各テストケースと検査結果から、正本の相対パス・節アンカー、対象の受入条件、正常・異常・境界値の区分、ケース名を特定できる形式とする。仕様値は正本への参照を使い、テスト用の別仕様書へ複製しない。

`spec-check`の確認手順は[仕様充足の検査](#仕様充足の検査)に従う。対応には承認対象の仕様版・コミット、実装のファイル・識別子、テストケースと検査結果の所在も含め、仕様だけが存在する状態と実装・検証済みの状態を区別する。内製機能・crateの新旧比較と差異・未検証条件の扱いは[憲章第8条](CHARTER.md#第8条-検証と事実の区別)を参照する。依存制約は[依存関係の検査](#依存関係の検査)、外部操作の隔離は[検証環境の制約](SECURITY_POLICY.md#検証環境の制約)を参照する。
