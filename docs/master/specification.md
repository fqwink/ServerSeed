# マスター管理構成仕様

[文書一覧](../DOCUMENT_INDEX.md)

## 責務

マスターは、Cloud対象の選択、接続、計画の確定、処理の開始と結果照合を担当する。必須台数・構築元・通常運用・対象別の実行入口は[運用条件](../POLICIES.md#実行入口と通常運用)を参照する。

本書はマスター固有の管理機能と同居する機能の統合を担当する。適用する機能の組み合わせは[構成の分離](../POLICIES.md#構成の分離)、構成値は[基本設定](../core/configuration.md#configyml)に従う。状態・排他・実行記録は[共通基盤](../core/common-platform.md)、SSH先の導入処理は[Cloud仕様](../core/cloud.md)を使用する。

## 対応範囲

[対象OSの条件](../core/product-scope.md#対応範囲)と、内包する[サーバ機能](../server/specification.md)・[マイニング機能](../mining/specification.md#対応範囲)の対応条件をすべて満たす物理PCを対象とする。サーバ機能だけが対応する機器を、マイニング機能も対応する機器と推測しない。構築元と通常運用の条件は[実行入口](../POLICIES.md#実行入口と通常運用)を参照する。

## 機能の統合

サーバ・採掘・管理の処理は一つの内蔵OS上で運用し、担当機能ごとに次の契約へ接続する。

| 担当機能 | 使用する正本と統合対象 |
|---|---|
| サーバ | [サーバ構成仕様](../server/specification.md)。Dockerアプリ、アプリ固有のバックアップ・検証・復旧を同じ定義から適用 |
| 採掘 | [マイニング構成仕様](../mining/specification.md)。機器検出、採掘サービス、監視・復旧を同じ定義から適用 |
| 管理 | 本書の対象登録、接続、計画・確認、SSH実行と結果照合 |

内包機能ごとに別の対象OS・構成選択を作らず、当該端末の[共通管理情報](../core/common-platform.md#初期構成選択と継続管理)へ結び付ける。マスター自身の構成・機器識別と、SSH先の対象構成・記録を分離する。ホスト全体への変更と機能間の衝突は[運用条件](../POLICIES.md#マスター管理構成の運用)に従う。

## 設定と管理情報

端末自身の基本設定・構成記録は[共通設定](../core/configuration.md#configyml)と[管理マーカー](../core/common-platform.md#管理マーカー)、内包機能の設定は[構成の分離](../POLICIES.md#構成の分離)を参照する。

マスター固有の対象一覧、接続先・ホスト鍵と対象IDの対応、計画・選択結果・対象操作との対応付けについて、設定ファイル名、配置、型・必須項目、更新・解除、版と移行方式は未確定とする。共通の`environment`を接続状態として流用せず、未知キーの拒否条件を緩めない。接続用秘密情報は[保存条件](../POLICIES.md#秘密情報)に従う。

バックアップ・復元に必要な管理情報の保全範囲は、形式の確定時に[データ保護の契約](../core/backups.md#未確定契約)へ対応付ける。旧二択形式との関係は[構成記録の互換性](../core/configuration.md#構成記録の互換性)を参照する。

## マスター固有のCLI

初期設定・対象登録、接続・検査、対象と操作・必須入力の選択、計画確認、適用・進捗、再接続・中断照合の具体的なコマンド名、オプション、出力形式は未確定とする。共通CLIの入力・出力契約は[CLI仕様](../core/cli.md)を参照し、構成値の`master`を定義したことを、同名コマンドの定義とは扱わない。

## 初期構築

1. [外部媒体の手順](../core/usb.md#セットアップ)で利用者がマスター管理構成を選択し、対応条件、必要入力と変更計画を確認する。
2. 物理PCの内蔵OSへ[機能の統合](#機能の統合)に沿って構成を適用し、[マスター設定](#設定と管理情報)の初期設定を行う。
3. [構成の検証](#構成の検証)と[内蔵OSの起動確認](../core/firmware.md#内蔵osの起動確認)を行い、内蔵OSから通常運用へ移行する。

マスター機能の初期設定入力、選択画面とCLIは[未確定契約](#未確定契約)の対象とする。

## 自動処理の流れ

1. マスター側で対象を識別し、インストール、セットアップ、更新、バックアップまたは復旧の操作を利用者が選択する。
2. SSH接続先の識別と認証を確認して接続し、[実行環境と対象OS](../core/cloud.md#実行環境と対象os)を分けて検査する。接続・検査だけで変更の実行を開始した扱いにしない。
3. 対象状態に応じて、構成、対象ディスク、必要な保存先と入力を利用者に提示する。選択・自動化の許可条件は[必須選択と自動実行](../POLICIES.md#必須選択と自動実行)に従う。
4. 対象の識別情報、変更内容、固定した成果物、バックアップ、管理経路、必要権限、再起動・再接続と復旧可否を計画に対応付け、必要な確認をマスター側で受ける。対象側の対話入力を放置して自動処理を待たせる方式にはしない。
5. 確定した計画を対象側の共通処理へ渡し、[実行側と対象側](../core/lifecycle.md#実行側と対象側)の責務に従って直列に適用する。対象OSへの導入・更新・バックアップの手順は各正本を使用する。
6. 必要な再起動後に同じ対象へ再接続し、対象側の状態・実行記録と検証結果を照合して、成功・失敗・未確認および残作業をマスターに表示する。

対象機器・計画・操作IDの対応、選択結果の受け渡し、記録の保存形式は下表で未確定として管理する。既存の[操作状態](../core/common-platform.md#操作状態)へ未定義の遠隔制御フィールドを追加したものと扱わない。

## 中断と結果照合

SSH切断、マスター停止、対象再起動で結果を受け取れなかった場合は、成功・未実行のどちらとも推測しない。対象側の操作状態・ロック・実配置と固定した計画を再取得して照合し、確認できるまで同じ変更の再投入や別の変更を開始しない。実行中・中断の扱いは[前回処理状態](../core/common-platform.md#前回処理状態)を参照する。

再接続先のホスト鍵や機器識別情報が変わった場合は、[管理経路の保護](../POLICIES.md#cloudの管理経路)に従った照合をOS再導入の計画に含める。マスターと対象の記録に不一致・欠損があれば、その範囲を未確認として提示する。

## 構成の検証

共通のOS・導入情報・構成記録を検査し、サーバ機能、採掘機能、管理機能ごとの結果を照合する。各担当仕様が要求するバックアップ・検証、管理機能の準備状態と、計画の対象に含まれるSSH操作の識別・接続・結果照合を確認する。いずれかの適用・検証が失敗・未確認なら、構成全体を完了・正常と報告せず、[状態判定](../core/common-platform.md#状態判定の優先順位)へ対応付ける。

更新・復旧の前後でも内包機能とマスター自身の管理情報を照合し、対象外の機能やSSH管理先を変更していないことを確認する。受入ケースへの対応は[CI/CD仕様](../core/ci-cd.md#三構成の受入条件)を参照する。

## 未確定契約

次の具体的な入力・形式・判定値は未確定であり、[仕様充足の判定](../POLICIES.md#実装着手と仕様充足の判定)を満たすまで依存する機能は実装しない。

| 対象 | 確定する契約と担当正本 |
|---|---|
| マスター初期設定・対象登録 | 本書の[設定と管理情報](#設定と管理情報)の具体化と初期構築への対応付け |
| 利用者インターフェース | 本書の[マスター固有のCLI](#マスター固有のcli)の確定と処理フローへの対応付け |
| SSH | 使用する外部実行物・固定版、ホスト鍵の信頼確立、認証、秘密情報の非平文管理、権限昇格、接続・実行の時間制限、転送と引用の安全性。本書の接続・制御責務と[外部依存台帳](../DEPENDENCY_EXCEPTIONS.md) |
| 実行制御 | 計画と対象・操作IDの結合、要求の配送と重複防止、対象側排他の確認、記録の照合、キャンセル・切断・再起動時の継続可否。本書の処理フローと[実行側と対象側](../core/lifecycle.md#実行側と対象側) |
| 再接続・復旧 | 本書の中断処理と、[Cloudの再接続契約](../core/cloud.md#未確定契約)・[マスター管理情報の復元](../core/backups.md#未確定契約)の対応付け |
| 同居制御 | CPU・GPU・メモリー・ストレージ・ネットワークの資源配分、サービス間の競合検出とホスト変更の調整、管理先未登録時を含む機能別の準備状態、途中失敗時の保全・再開・切り戻しの具体契約と受入ケース |

本書のフロー定義を、これらの契約が完成したことや実機で動作確認済みであることの根拠にしない。
