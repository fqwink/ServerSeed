# 宣言型構成管理（内製IaC）

[文書一覧](../DOCUMENT_INDEX.md)

## 責務と適用範囲

本書は、[内製IaC方針](../PRINCIPLES.md#内製iac)に基づくCoreの構成管理について、定義解析、実状態の取得、差分と計画、適用制御および結果検証の責務を定める。適用の許可・禁止は[宣言型構成管理の適用条件](../POLICIES.md#宣言型構成管理の適用条件)を参照する。

初期の限定対象は、ServerSeedが管理するファイル・ディレクトリとその権限とする。パッケージ・systemdサービスの宣言型管理、その後の外部媒体・SSH経路との統合を段階的に扱う。段階ごとの実施先と進捗は[ロードマップ](../ROADMAP.md)を参照する。この対応順序は宣言型管理の拡張順であり、既存のOS導入や構成固有機能の責務を削除・移管するものではない。

対象OS・CPUと事業者資源との境界は[製品の対応範囲](product-scope.md#対応範囲)、各構成が適用する機能は[構成の分離](../POLICIES.md#構成の分離)に従う。OS導入、バックアップ、採掘監視およびアプリ固有の検証・復旧そのものを、ファイル資源の適用だけで代替しない。

## 入力と状態の区分

次の三つを区別して処理へ渡す。本表は意味上の区分であり、新しい設定キー・JSONフィールド・保存形式を定義するものではない。

| 区分 | 処理で使用する情報 |
|---|---|
| 望ましい構成 | 選択済み構成に適用する定義と、確定した利用者入力から求める資源・属性の要求。形式と解析は[共通設定](configuration.md#構成定義の解析)、収録定義は[組込み資材](../PRINCIPLES.md#組込み資材)を参照 |
| 観測した実状態 | 識別した対象OSの資源から実際に取得した内容・属性、取得条件と確認不能事項。取得不能を資源の不在や要求との一致として扱わない |
| 適用記録 | 計画・操作に対応する実施内容と検証結果。過去の適用結果を、現在の実状態を観測した結果の代わりにしない |

対象機器、実行環境と対象OSの対応は[共通基盤](common-platform.md#実行環境と管理対象)へ照合する。共通の状態名と[状態スナップショット](common-platform.md#状態スナップショット)の意味は維持し、IaC用の別の総合状態や状態の正本を設けない。

## 資源の識別と管理範囲

資源は、対象機器・対象OS、担当責務、資源種別と対象内の識別情報へ対応付ける。ファイル・ディレクトリでは配置先と管理する属性を特定し、同じパス名でもLive環境・マスター・SSH管理先を別の対象として区別する。

差分を求める前に、選択済み構成が管理する資源と属性、対象外の資源と属性、複数機能が共有する資源を識別する。ファイルシステム上に存在することや、親ディレクトリを管理することだけで、その配下全体を管理対象に取り込まない。所有範囲・競合による停止と、定義から外れた資源の扱いは[適用条件](../POLICIES.md#宣言型構成管理の適用条件)に従う。

識別子の具体形式、管理範囲の表現、パスの検証と同一資源の判定は[未確定契約](#未確定契約)とする。既存の設定項目や管理マーカーだけで、資源単位の管理範囲が確定したとは扱わない。

## 処理フロー

次の処理を既存の[ライフサイクル](lifecycle.md#構成適用との接続)へ接続する。

1. 定義を解析し、対応する形式・版、型、必須項目と資源の管理範囲を照合する。解析契約は[構成定義の解析](configuration.md#構成定義の解析)を参照する。
2. 対象OSから管理属性を観測し、望ましい構成・実状態・適用記録を区別して照合する。観測結果の欠損・取得不能は計画の停止理由へ対応付ける。
3. 管理対象の差分から、適用する資源・属性、処理順序、影響、前提条件、保全・復旧可能範囲を求め、[更新計画](lifecycle.md#更新計画)へ対応付ける。競合・前提不足・未対応は実行不能理由として扱う。
4. 必須選択と計画確認を終えた変更操作で、[共通ロック](common-platform.md#ロックおよび同時実行)の下で対象、定義と観測した前提を再照合する。確認後の条件変化には更新計画の破棄・再検査・再確認を適用する。
5. 確定した差分だけを適用し、資源ごとの適用位置と結果を親の計画・操作へ対応付ける。ファイル置換は[原子性](common-platform.md#原子性と書き込み)、OSコマンドの呼び出しは[外部コマンド実行](common-platform.md#外部コマンド実行)の契約を使用する。
6. 実資源を再取得して要求と照合し、適用済み範囲、失敗・未確認と残作業を判別する。結果は[操作状態](common-platform.md#操作状態)と[実行履歴](common-platform.md#実行履歴)へ対応付け、構成全体の検証は各構成の担当仕様へ接続する。

計画作成と読み取り専用の差異検出では、[読み取り専用時の記録処理](common-platform.md#読み取り専用時の記録処理)を使用する。計画・資源別結果の具体形式と既存出力への対応は未確定であり、上記の流れだけで既存のJSON例に資源単位の情報を表現済みと扱わない。

## 再適用と差異検出

再適用では、現在の実状態から管理属性の差分を再計算し、前回の計画や成功記録をそのまま再実行しない。一致する属性と変更が必要な属性を分け、[適用条件](../POLICIES.md#宣言型構成管理の適用条件)の不要な書き換え・再起動の禁止へ照合する。比較・正規化と前提条件の同一性判定は[未確定契約](#未確定契約)で管理する。

読み取り専用の検査で見つかった差異は、事実、影響と必要な操作候補として既存の[CLI出力](cli.md#共通json出力)へ対応付ける。差異の表示だけで変更工程へ移行せず、具体的な出力項目はCLI契約の確定時に定める。

## 中断と復旧

中断時は資源ごとの実適用位置、実状態と記録を親の計画・操作に照合し、適用済み・未適用・確認不能の範囲を識別する。再開・再投入には[憲章第11条](../CHARTER.md#第11条-再開と工程通過)、総合状態の判定には[前回処理状態](common-platform.md#前回処理状態)を適用する。遠隔応答の欠損は[マスターの結果照合](../master/specification.md#中断と結果照合)へ接続する。

復旧計画では、資源別に保全元、変更前後の状態、復元方法、検証方法と復旧できない範囲を対応付ける。適用の失敗と復旧の成否を分け、[ロールバックの制約](../POLICIES.md#ロールバック)に照合する。本体置換専用のトランザクション形式を、任意資源の復旧形式として流用済みとは扱わない。

資源別の記録・保全・復旧の具体契約は下表の未確定事項とする。記録が不足する範囲を未適用と推測せず、照合不能な資源に依存する後続の変更を進めない。

| 資源定義 | 本書の識別子・種別・管理属性、型・必須性・許容範囲、管理範囲と既存資源の取り込み、配置・版・移行。設定ファイルとの接続は[共通設定](configuration.md)へ対応付ける |
| パスとファイル操作 | 対象ルート内の解決・除外条件、シンボリックリンク・親ディレクトリ・特殊ファイル等の検査、検査後の差し替え対策、内容・所有者・権限の比較と変更方法。既存の[保護条件](../POLICIES.md#導入先と一時ファイル)と原子性への対応 |
| 差分と計画 | 比較・正規化、競合検出、依存順序・循環の扱い、同じ入力・実状態に対する計画の再現性、確認した定義・対象・前提の固定と再照合方法、資源別結果と[計画形式](lifecycle.md#更新計画)・[CLI](cli.md)との接続 |
| 適用と中断 | 資源別の入出力・副作用・停止位置、使用するOS機能と外部コマンド・引数・例外ID、時間・資源上限、再試行・キャンセル、親操作の排他と記録確定への対応 |
| 記録と復旧 | 資源別の実施・検証記録の形式・保存先・版・互換性、保全と復元確認、中断時の照合、復旧手順と復旧不能範囲。共通の[バックアップ契約](backups.md#未確定契約)へ対応付ける |
| 入口の統合 | [外部媒体の引き継ぎ](usb.md#更新バックアップ復旧)、[実行側と対象側](lifecycle.md#実行側と対象側)、[マスター制御](../master/specification.md#未確定契約)の担当契約との接続 |
