# 共通基盤と状態管理

[文書一覧](../DOCUMENT_INDEX.md)

## 共通基盤と構成の分離

構成の共通化と責務分離は[基本方針](../PRINCIPLES.md#共通基盤と責務分離)に従う。

| 区分 | 責任 |
|---|---|
| 共通基盤 | Ubuntu Server導入、外部媒体・Cloudで再利用する適用制御、機器検出、署名検証、更新・バックアップ・検証・復旧の共通手順、排他制御、履歴 |
| マスター管理構成 | [機能の統合と管理制御](../master/specification.md#機能の統合) |
| サーバ構成 | [サーバ構成の責任範囲](../server/specification.md#責任範囲) |
| マイニング構成 | [マイニング構成仕様](../mining/specification.md) |

機器検出と構成選択の関係は[構成選択と継続管理](../POLICIES.md#構成選択と継続管理)を参照する。

### 実行環境と管理対象

状態判定と管理記録は、検査・変更する対象ディスクまたは対象OSに結び付ける。対象OSと、その処理を制御する外部媒体のLive環境・マスター・SSH一時実行環境を識別し、対象側の記録を制御環境自身の情報で代用しない。Cloudの識別は[実行環境と対象OS](cloud.md#実行環境と対象os)、適用時の制御・保存は[実行側と対象側](lifecycle.md#実行側と対象側)に従う。

マスター自身も選択済み構成を持つ管理対象とし、SSH管理先の対象OS・構成・操作状態とは分離する。マスター固有の管理情報は[担当仕様](../master/specification.md#設定と管理情報)を参照する。

## 本体導入と構成管理

本体と構成セットアップの関係は[本体導入](../POLICIES.md#本体導入)、実行手順は[バイナリ導入](lifecycle.md#バイナリ導入)を参照する。

本体の現在の導入情報は`/var/lib/serverseed/install.json`に保存する。

```json
{
  "schema_version": 1,
  "status": "installed",
  "serverseed_version": "0.1.0",
  "architecture": "amd64",
  "binary_sha256": "hex",
  "installed_at": "RFC3339"
}
```

`status`は`installed`または`removed`とする。`removed`は本体削除が正常終了したことを表し、バージョンとハッシュは削除した本体の情報を保持する。導入情報は現在状態の記録であり、追記型の履歴にはしない。

導入情報と管理情報は[状態判定の優先順位](#状態判定の優先順位)で対象OSを確認した後に評価する。管理マーカーのない対応OSは、本体導入済みでも`ADOPTABLE`とする。`installed`の記録と実ファイルが不一致、または本体変更操作が未完了なら`RECOVERABLE`とする。正常に本体を削除した未管理OSは`ADOPTABLE`であり、設定やログが残るだけで破損と判定しない。管理マーカーが残るOSは、導入情報にかかわらず管理対象として整合性を検査する。

## 初期構成選択と継続管理

構成の選択・継続管理・変更の条件は[構成選択と継続管理](../POLICIES.md#構成選択と継続管理)に従う。選択結果の形式は[共通設定](configuration.md#configyml)と[管理マーカー](#管理マーカー)を参照する。

選択結果は一つの構成値として管理マーカーの`profile`、状態スナップショットの`serverseed.profile`、構成選択済みの実行履歴の`profile`へ対応付ける。マスターが内包する機能を理由に、記録ごとに別の構成値を保存しない。形式・版の互換性は[構成記録の互換性](configuration.md#構成記録の互換性)、内包機能の検証は[マスター管理構成](../master/specification.md#構成の検証)を参照する。

## 共通状態判定

ServerSeedは対象ディスクまたは対象OSを検査し、次の状態に分類する。

| 状態 | 意味 |
|---|---|
| `EMPTY` | OSが存在しない |
| `ADOPTABLE` | 対応OSだが構成セットアップ未完了 |
| `MANAGED` | ServerSeed管理対象OS |
| `RECOVERABLE` | 導入・管理対象で、変更未完了、導入情報の不整合、正常起動または構成の問題がある |
| `UNKNOWN` | 未対応OS、判定不能または安全未確認 |

状態別の基本動作は[状態に応じた基本動作](../POLICIES.md#状態に応じた基本動作)を参照する。

管理対象であることは、少なくとも次の情報を使用して判定する。

- OSおよびバージョン
- ルートファイルシステム
- `/etc/os-release`
- ServerSeed管理マーカー
- マシン識別情報
- ServerSeed構成バージョン
- 前回処理の完了状態

主要な管理情報の配置は[管理ファイル一覧](configuration.md#管理ファイル一覧)を参照する。

単にOSらしいファイルが存在するだけでは、管理対象と判定しない。

### 状態判定の優先順位

状態判定は安全側に倒すため、次の順に検査し、最初に該当した状態を採用する。

1. 対象ディスクまたは存在するルートファイルシステムを読み取れない場合は`UNKNOWN`とする。
2. 外部媒体またはSSH実行環境から識別した対象ディスクで、パーティション、OS、ブートローダーが存在せず、導入・構成管理の記録もないことを確認できる場合のみ`EMPTY`とする。実行環境の起動ディスクと混同しない。
3. それ以外の対象は[対応OSの判定](product-scope.md#ubuntu-2404-lts判定)を行う。未対応OS、OS情報の欠損・読み取り不能、または対応を確認できない場合は`UNKNOWN`とする。管理マーカーがあってもこの判定を省略しない。
4. [前回処理状態](#前回処理状態)が未完了、[本体導入情報](#本体導入と構成管理)が不整合・未完了、または構成管理の証跡がある対象で起動構成・必須管理ファイルの欠損・破損・不正、保存済み構成の不明・不正・不一致を検出した場合は`RECOVERABLE`とする。内包機能の必須項目も、[機能適用の範囲](../POLICIES.md#構成の分離)に対応付けて検査する。
5. [管理マーカー](#管理マーカー)、マシン識別情報、構成バージョンおよび保存済み構成が整合する場合は`MANAGED`とする。
6. 管理マーカーがなく、[本体導入と構成管理](#本体導入と構成管理)の条件を満たす対応OSは`ADOPTABLE`とする。Cloud版では[導入の前提](cloud.md#前提)も確認する。
7. 上記に該当しない場合は`UNKNOWN`とする。

構成管理の証跡は、検査対象の管理マーカー、またはその対象に構成を適用した操作記録を指す。本体だけの導入・正常削除の記録を構成管理の証跡と扱わず、構成未セットアップ時の管理マーカー・構成設定・構成固有ファイルの未作成だけで手順4へ該当させない。

`EMPTY`は内容の判定であり、ディスクへの書き込み許可ではない。OSが見つからないだけで空ディスクと推測せず、既存パーティションや管理記録がある場合は手順2を満たさない。Cloudの導入能力は[対象識別](cloud.md#実行環境と対象os)、消去可否は[ディスク操作](../POLICIES.md#ディスク操作)で別に判定する。

### 管理マーカー

管理マーカーの検査には[状態判定の優先順位](#状態判定の優先順位)を適用する。`/etc/serverseed/managed`はJSON形式とし、少なくとも次を含める。

```json
{
  "managed": true,
  "machine_id": "string",
  "created_at": "RFC3339",
  "serverseed_version": "0.1.0",
  "config_revision": 1,
  "migration_revision": 0,
  "profile": "server"
}
```

`profile`は[`config.yml`](configuration.md#configyml)の`serverseed.profile`と一致しなければならない。欠損、不正値または不一致の場合は`RECOVERABLE`とする。

`managed`が`true`でない場合、または`machine_id`が`/etc/serverseed/machine-id`と一致しない場合は`MANAGED`と判定しない。

### 前回処理状態

前回処理の記録形式とプロセスの確認方法は[操作状態](#操作状態)を参照する。

前回処理が`running`、`interrupted`、または終了状態不明のまま残っている場合は`RECOVERABLE`とする。継続可否は[未完了操作](../POLICIES.md#未完了操作)に従う。実行中の操作に属する診断は[トランザクション診断](cli.md#doctor)として区別し、新しい変更操作を並行開始しない。

### 状態スナップショット

`/var/lib/serverseed/state.json`は現在の判定結果を保存する。ファイルは再生成可能なキャッシュとして扱い、判定の唯一の根拠にしてはならない。このキャッシュの生成・更新は、[CLIの変更可否](../POLICIES.md#コマンド別の変更可否)に定める管理状態の変更に含める。

```json
{
  "schema_version": 1,
  "state": "MANAGED",
  "detected_at": "RFC3339",
  "machine_id": "string",
  "os": {
    "id": "ubuntu",
    "version_id": "24.04",
    "kernel": "string"
  },
  "boot": {
    "mode": "uefi",
    "secure_boot": "unknown"
  },
  "serverseed": {
    "installed": true,
    "profile": "server",
    "version": "0.1.0",
    "config_revision": 1,
    "migration_revision": 0
  },
  "checks": [
    {
      "id": "os.supported",
      "result": "pass",
      "message": "Ubuntu 24.04 LTS detected"
    }
  ]
}
```

`state`は[共通状態判定](#共通状態判定)の状態名を使用する。`checks[].result`は`pass`、`warn`、`fail`、`unknown`のいずれかとする。

構成未選択の場合、`serverseed.profile`、`config_revision`および`migration_revision`は`null`とし、未確定の値を生成しない。`serverseed.installed`は管理対象判定ではなく、検査対象OSの本体導入状態を表す。外部媒体・マスター・SSH一時環境上の実行本体を、対象OSへ導入済みと取り違えない。

### 操作状態

`/var/lib/serverseed/operation.json`は実行中または直近の変更操作を表す。

変更操作の開始時に実行中状態を記録し、成功または失敗の確定時に終了状態を記録する。

```json
{
  "schema_version": 1,
  "operation_id": "string",
  "command": "update",
  "status": "running",
  "started_at": "RFC3339",
  "finished_at": null,
  "pid": 1234,
  "plan_id": "string",
  "lock_path": "/var/lib/serverseed/lock"
}
```

`status`は`running`、`success`、`failed`、`interrupted`のいずれかとする。変更操作の開始時に`running`を記録できない場合、その操作を開始してはならない。

独立した本体変更操作では`command`を`self install`、`self update`、`self uninstall`のいずれかとし、構成未選択の実行履歴では`profile`を`null`にする。通常の`update`内では親の操作ID・ロックを引き継ぎ、親の`command`を上書きしない。初回は権限を確認して管理ディレクトリとロックを用意した後に操作状態を記録し、配置を開始する。

処理中にプロセスが終了し、`running`のまま残った場合、次回起動時にPIDの存在と開始時刻を確認する。実行中プロセスが確認できない場合は`interrupted`として扱う。

### 読み取り専用時の記録処理

[コマンド別の変更可否](../POLICIES.md#コマンド別の変更可否)と[成果物の保存](../POLICIES.md#成果物の保存)に従い、読み取り専用コマンド、`plan`および`--dry-run`では、検出した中断をメモリ上の判定として報告する。`operation.json`の書き戻し、状態キャッシュの生成・更新、実行履歴への追記、既定保存先への自動的なログ・レポート出力は行わず、初期化のための管理ディレクトリやロックファイルも作成しない。診断情報は標準出力または標準エラーへ出す。利用者が明示した成果物の保存だけは上記ポリシーの条件に従う。

中断記録の永続化や後始末は、変更を許可された復旧・変更操作が[共通ロック](#ロックおよび同時実行)の下で状態を再検査して行う。実行中の親操作に属する[トランザクション診断](cli.md#doctor)も記録を変更せず、親が保持するロック・操作IDを照合して読み取り専用の診断を行う。

## ロックおよび同時実行

同時実行の許可条件は[変更操作の排他](../POLICIES.md#変更操作の排他)を参照する。

変更操作は`/var/lib/serverseed/lock`を使用して排他制御する。本体変更と構成・OSの変更も同じロックを使用し、子処理へ分ける場合も検証と操作状態の確定までロックを維持する。読み取り専用操作のロック取得条件は[変更操作の排他](../POLICIES.md#変更操作の排他)を参照する。

ロック競合と解除の扱いも[変更操作の排他](../POLICIES.md#変更操作の排他)に従う。

## 原子性と書き込み

ServerSeedが管理する設定、状態、履歴およびレポートを書き換える場合は、一時ファイルへ書き込み、同期し、同一ファイルシステム内のrenameで置き換える。利用者指定先への成果物保存は[CLIの成果物保存](../POLICIES.md#成果物の保存)に従い、管理ファイルの置換とは区別する。本体置換の手順と中断時の扱いは[本体の置換と復旧](lifecycle.md#本体の置換と復旧)に従う。

重要な管理ファイルの部分書き込み、空ファイル化、不完全なJSONまたはYAMLを残してはならない。管理ファイルの書き込み失敗時は失敗状態を記録し、次回起動時に`RECOVERABLE`として扱う。

## 外部コマンド実行

ServerSeedが外部コマンドを実行する場合は、引数配列として実行し、シェル展開に依存しない。

外部コマンドの標準出力、標準エラー、終了コード、実行時間を記録する。記録先は[読み取り専用時の記録処理](#読み取り専用時の記録処理)に従って区別し、ログ出力時の秘匿化は[秘密情報の扱い](../POLICIES.md#秘密情報)に従う。

タイムアウトを持たない外部コマンドを実行してはならない。タイムアウト時は処理を失敗として記録し、後続の変更操作を停止する。

## 実行履歴

`/var/lib/serverseed/history.jsonl`は1行1JSONとし、操作ごとに追記する。

各行は少なくとも次を含める。

```json
{
  "operation_id": "string",
  "command": "update",
  "started_at": "RFC3339",
  "finished_at": "RFC3339",
  "result": "success",
  "profile": "server",
  "serverseed_version_before": "0.1.0",
  "serverseed_version_after": "0.1.1"
}
```

履歴ファイルの書き込みに失敗した場合、変更操作は成功として扱わない。

## ログ形式

ファイルへの記録を許可された操作のログは、人が読むテキストログと機械処理用JSONLを分けて保存する。読み取り専用操作の扱いは[読み取り専用時の記録処理](#読み取り専用時の記録処理)を参照する。

保存先は[共通設定の管理ファイル一覧](configuration.md#管理ファイル一覧)を参照する。

ログの秘匿化は[秘密情報の扱い](../POLICIES.md#秘密情報)に従う。
