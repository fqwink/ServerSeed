# 本体導入・更新・復旧と署名検証

[文書一覧](../DOCUMENT_INDEX.md)

## 実行側と対象側

導入・保守の利用者向け入口は[実行入口と通常運用](../POLICIES.md#実行入口と通常運用)に従う。本書の取得・本体管理・更新は、その入口から確定した計画を適用する共通手順とし、独立した手動導入経路として案内しない。

| 実行側 | 共通処理への接続 |
|---|---|
| 外部媒体 | [USB手順](usb.md)で対象内蔵OSを識別し、対象OS内の処理とLive環境側の制御を分ける |
| マスター | [マスター管理](master-management.md)が選択・計画・接続を制御し、[Cloud手順](cloud.md)から対象側の共通処理を呼び出す |
| 対象OS | 本体配置、構成、サービス、状態・操作・履歴を自身の管理領域へ記録し、検証結果を実行側へ返す |

マスターや一時実行環境で`self`を実行しただけでは、対象OSへ本体を配置したことにならない。OS未導入時は対象OSの用意を[物理PC](usb.md#セットアップ)または[Cloud](cloud.md#osのインストール)の手順で先に行う。

対象の操作状態・ロックを実行側へコピーして対象側の管理を代替しない。OS導入前・再起動中を含む制御側と対象側の操作ID・ロックの引き継ぎ、要求の重複防止と記録の保存・照合形式は未確定とし、[マスター制御契約](master-management.md#未確定契約)または[媒体からの引き継ぎ](usb.md#更新バックアップ復旧)の確定を着手条件とする。

## バイナリ導入

配布形式とOSパッケージ管理との境界は[バイナリ配布](../PRINCIPLES.md#バイナリ配布)を参照する。

本体へ収録する資材とリビジョンの対応は[組込み資材](../PRINCIPLES.md#組込み資材)を参照する。

### 初回の取得と配置

1. 対象OS、CPU、管理権限と実行時依存を確認する。入口側で確定したバージョンについて、[配布先](ci-cd.md#成果物保管)からマニフェスト、署名および該当バイナリを権限を制限した作業領域へ取得する。ISOに収録した同じファイル一式や、検証済みの搬入物も使用できる。
2. [信頼鍵の初回導入と更新](../POLICIES.md#信頼鍵の初回導入と更新)と[署名およびチェックサム](#署名およびチェックサム)に従い、既存の`gpgv`と`sha256sum`で確認する。実行時依存が欠ける場合は不足項目を表示し、実行や本体配置を開始しない。
3. 検証済みバイナリを絶対パスで指定し、対象OS内で[selfコマンド](cli.md#self)の`install`を実行する。本体の`version --json`とマニフェストのバージョンが一致することを確認する。
4. root権限、配置先の所有権、競合する実行本体、空き容量、既存の導入情報と未完了操作を確認し、計画・確認を経て[本体の置換と復旧](#本体の置換と復旧)を実行する。
5. [管理対象サーバのディレクトリ](configuration.md#管理対象サーバのディレクトリ)と[権限](../POLICIES.md#ファイル権限)に従って配置し、必要な管理ディレクトリと共通ポリシーの初期値を用意する。初回の信頼済みキーリングは未配置の場合のみ登録する。
6. 配置した本体のバージョン・ハッシュと読み取り専用診断を確認し、[本体導入情報](common-platform.md#本体導入と構成管理)を確定する。設定未作成は構成セットアップ待ちとして入口側へ通知し、確認済みのセットアップ計画があれば次の工程へ進む。

初回導入時の変更範囲と設定保持は[初回導入の保護条件](../POLICIES.md#初回導入の保護条件)を参照する。

### 既存配置と再導入

導入情報に一致する同一バージョン・ハッシュが配置済みの場合は、検査結果を返して正常終了し、設定を再生成しない。新しいバージョンへの変更は`self update`、記録と実ファイルの不一致は`recover --self`へ誘導する。

既存配置との競合時は[競合配置の保護](../POLICIES.md#競合配置の保護)に従う。

### 本体だけの削除

削除の許可条件と保持対象は[本体だけの削除](../POLICIES.md#本体だけの削除)、トランザクションは[本体の置換と復旧](#本体の置換と復旧)を参照する。

## アップデート

### 更新対象

対象ごとの適用方法は[更新対象](../POLICIES.md#更新対象)を参照する。

### 更新元

更新元は抽象化し、次を利用できるようにする。

- ServerSeed USB
- 署名付きHTTPSリポジトリ
- ローカルディレクトリ
- 手動搬入した更新パッケージ

更新元の選択条件は[更新元](../POLICIES.md#更新元)を参照する。

### 候補の固定

既定候補、計画時の固定と再照合は[候補の固定](../POLICIES.md#候補の固定)を参照する。

### 更新前検査

更新開始前に少なくとも次を確認する。

- 更新情報の署名
- ファイルのチェックサム
- 対象マシン、管理状態および保存済み構成の整合性
- 更新成果物が共通基盤または選択済み構成を対象としていること
- 現在と更新後のバージョン
- OS互換性
- ディスク空き容量
- パッケージ管理の正常性
- SSDまたはストレージ状態
- バックアップの最終成功状態
- 前回処理が完了していること
- SSHまたはコンソールによる復旧経路

検査結果による実行可否は[共通の安全条件](../POLICIES.md#共通の安全条件)に従う。

### 更新処理

1. 更新情報を取得して検証する。
2. 変更予定を事前検査する。
3. 現在の設定とバージョン情報を保存する。
4. 必要なデータバックアップを確認または実行する。
5. OSおよび対象アプリを更新する。
6. 必要な構成移行を実行する。
7. サービスを起動または再読み込みする。
8. ヘルスチェックおよび総合検証を行う。
9. 本体変更が計画されている場合は、[本体の置換と復旧](#本体の置換と復旧)を最後の変更ステップとして実行する。
10. 成功状態または失敗状態を記録する。
11. 再起動の要否を表示する。

処理中の失敗は[共通の安全条件](../POLICIES.md#共通の安全条件)に従う。

### ロールバック

復元対象とダウングレードの制約は[ロールバック](../POLICIES.md#ロールバック)を参照する。

### 本体の置換と復旧

本体だけの更新で変更できる記録と構成互換性の条件は[本体更新の変更範囲](../POLICIES.md#本体更新の変更範囲)に従う。

本体変更では、[共通ロック](common-platform.md#ロックおよび同時実行)の取得後に状態を再検査し、次の手順を使用する。

1. 対象OS・CPU、導入情報、署名、保存済み構成に対する互換範囲、必要容量、復旧経路を確認する。通常の導入・更新ではSemVerで現在より古い本体を拒否する。同一バージョンで異なるハッシュの成果物も拒否する。
2. `/var/lib/serverseed/self-transaction/`に候補のマニフェスト・署名・ビルドメタデータ、変更前の導入情報と本体のハッシュ、管理対象の場合はバージョン記録の退避を保存する。本体は配置先と同一ファイルシステムの`/usr/local/bin/.serverseed.new`へ排他的に取得・コピーし、同期後に署名付きハッシュと再照合する。既存の一時ファイルを無条件に上書きしない。
3. 候補の絶対パスで`version --json`を実行し、バージョン、アーキテクチャと互換性情報を照合する。正常版がある場合は、その本体、`/var/lib/serverseed/release/`に保持した検証情報および導入情報を`/var/lib/serverseed/previous/`へ保全する。検証情報が欠ける状態で正常版と推測しない。
4. トランザクションの`phase`を`prepared`として永続化し、[共通の原子性](common-platform.md#原子性と書き込み)に従うrenameで配置本体を置き換える。実行中ファイルへの上書き書き込みは行わない。置換後は`phase`を`replaced`として記録する。
5. 配置後の本体を絶対パスで起動し、`version --json`と[トランザクション診断](cli.md#doctor)を検査する。成功したら導入情報と、管理対象の管理マーカー・バージョン記録を更新する。現在版のマニフェスト・署名・ビルドメタデータは`/var/lib/serverseed/release/`へ保持し、次回の更新・復旧にも使用する。
6. `phase`を`verified`として同期し、操作状態と実行履歴を確定してから一時領域を清掃する。記録失敗を含めてすべて成功するまで、ロックを解放せず成功を返さない。

トランザクションの記録は同ディレクトリの`state.json`とし、`schema_version: 1`、`operation_id`、`command`、`phase`、`before_sha256`、`after_sha256`、`staged_path`および`previous_path`を含める。初回の変更前ハッシュ・退避先は`null`とする。パスは上記の生成先に限定し、外部入力のパスを復旧時の書き込み先にしない。

配置後の検証に失敗した場合は、事前計画で許可された範囲で次の復旧手順を直ちに試み、元の操作は失敗として返す。復旧完了前に別の通常変更へ進まない。単なるSSH切断・結果未着は配置後検証の失敗と同一視せず、[中断と結果照合](master-management.md#中断と結果照合)を先に行う。

中断後の`recover --self`は、署名付き候補・退避本体、導入情報、実配置ハッシュとトランザクションを照合する。配置が候補と一致し診断に成功する場合は記録を完了できる。それ以外は署名と現在の設定に対する互換性を確認した正常版へ戻し、元の操作は失敗または中断として記録する。rename直後で`prepared`のままでも、実配置ハッシュから処理位置を確認する。

初回導入に退避本体がない場合は、記録に一致する候補での導入完了、または今回新規配置した本体だけの除去を計画として提示する。対象を特定できない場合、署名を検証できない場合、または旧版が移行後の設定を扱えない場合は変更せず停止し、管理者の復旧を要求する。無関係な設定・データを巻き戻して本体だけの復旧を成功させない。

`self uninstall`は候補の取得・置換・起動検査を行わない。導入情報と現在版の署名付き検証情報を照合し、退避して`prepared`を記録した後に配置本体だけを除去する。除去後を`replaced`とし、実ファイルが存在せず保護対象が保持されていることを検査して導入情報を`removed`へ更新する。`after_sha256`と`staged_path`は`null`とし、最後に`verified`・操作結果を確定する。中断時はこの組み合わせを識別し、削除完了の確定か退避版の復元を計画する。配置対象が別ファイルへ変わっていた場合は削除しない。

### 更新計画

`update`、`setup`、`recover`および`self`の変更操作は、変更開始前に計画を作成する。計画は人間向けに表示し、`--json`では構造化して出力する。

```json
{
  "schema_version": 1,
  "plan_id": "string",
  "command": "update",
  "created_at": "RFC3339",
  "target_state": "MANAGED",
  "requires_confirmation": true,
  "requires_reboot": false,
  "steps": [
    {
      "id": "backup.check",
      "title": "Check last backup",
      "destructive": false,
      "requires_network": false
    }
  ],
  "blocked_by": []
}
```

`blocked_by`が空でない計画は実行してはならない。計画作成のみを行う場合の変更可否と成果物の保存は[CLIのplan](cli.md#plan)に従う。

本体変更の計画には、取得元、固定したバージョン、候補ハッシュ、現在と変更後の配置、必要容量、既存設定への影響、退避先および復旧可否を含める。確認後に取得内容や前提条件が変わった場合は計画を破棄し、再検査・再確認する。

OS導入、独立バックアップおよびマスター制御の計画に必要な追加入力・出力形式は、[Cloud](cloud.md#未確定契約)、[バックアップ](backups.md#未確定契約)、[マスター](master-management.md#未確定契約)の契約確定時に本節へ対応付ける。上記の既存JSON例に未定義の値を埋めて、遠隔実行や新しい操作を表現済みと扱わない。

### 計画時と実行時の検証

本体の導入・更新を対象とする`plan`と`--dry-run`では、マニフェストの署名、参照するビルドメタデータのハッシュ・内容、固定した候補情報とローカルの前提条件を検査する。HTTPSのメタデータはメモリ上で処理し、本体の取得・配置・起動、一時ファイルや管理ディレクトリの作成は行わない。本体削除の計画は保存済み導入情報と現在版の検証情報を対象とし、新しい候補を取得しない。

計画だけの検査で未実施の本体ハッシュ照合・起動診断を検証済みと表示しない。未実施の範囲と実行時に必要な検証を、人間向けの要約と[共通JSON出力](cli.md#共通json出力)の`warnings`で示す。署名不正、メタデータ不一致、ローカル前提の不成立など、その段階で検出した問題は計画の`blocked_by`へ含める。

実行を要求された導入・更新では、取得を伴う準備も所定の計画・確認の範囲内で行い、[署名およびチェックサム](#署名およびチェックサム)と[本体の置換と復旧](#本体の置換と復旧)に従って候補の本体ハッシュ・バージョン・互換性を検証する。その結果を適用用の計画へ反映し、検証がすべて成功した場合だけ適用へ進む。準備の結果、確認済みの候補・変更内容・前提条件に差異が生じた場合は、[更新計画](#更新計画)に従って計画を破棄し、再検査・再確認する。計画だけの検査結果を、取得後の検証や適用の確認の代わりにしない。

### 署名およびチェックサム

本体用の[更新マニフェスト](#更新マニフェスト)と、ISO用の[媒体マニフェスト](usb.md#媒体マニフェスト)はOpenPGP detached signatureで真正性を確認し、記載されたSHA-256で成果物を検証する。初回の信頼確立、鍵の更新と失効は[信頼鍵の初回導入と更新](../POLICIES.md#信頼鍵の初回導入と更新)に従う。

署名検証には`gpgv`を使用し、信頼する公開鍵はServerSeed管理用キーリングに保存する。

```text
/etc/serverseed/trustedkeys.gpg
```

実行を伴う初回導入と更新は次の順序で検証する。計画だけを作成する場合は[計画時と実行時の検証](#計画時と実行時の検証)の範囲を適用する。

1. 更新マニフェストの署名を検証する。
2. マニフェスト内の対象バージョン、互換性および必須条件を検査する。初回は構成を選択せず、共通基盤として両構成に対応する本体を選ぶ。管理対象では保存済み構成も照合する。
3. 取得済みファイルのSHA-256チェックサムを検証する。
4. すべて成功した場合のみ適用用計画の検証を完了し、[更新計画](#更新計画)の確認条件に従って適用へ進む。

署名検証またはチェックサム検証に失敗した更新は適用しない。

初回の検証は、未導入のServerSeedではなく既存の検証ツールで行う。信頼したキーリングを`KEYRING`、取得したマニフェストと署名を`MANIFEST`と`SIGNATURE`とした場合、`gpgv --keyring KEYRING SIGNATURE MANIFEST`で署名を検証した後、構造化パーサーで対象エントリを選び、`sha256sum`の結果と照合する。取得したJSONをシェルとして評価しない。

### バージョン管理

ServerSeed本体、構成定義、マイグレーションにはそれぞれバージョンを持たせる。

バージョン形式はSemantic Versioningを基本とする。ただし、構成定義とマイグレーションは互換性判定のために独立した整数リビジョンを併用できる。

管理対象サーバには、少なくとも次を記録する。

```text
serverseed_version
config_revision
migration_revision
last_successful_operation
last_successful_operation_at
```

## 更新マニフェスト

更新マニフェストはJSON形式とし、署名対象に含める。

```json
{
  "schema_version": 2,
  "serverseed_version": "0.1.0",
  "config_revision": 1,
  "migration_revision": 0,
  "target_profiles": ["server", "mining"],
  "target_os": {
    "id": "ubuntu",
    "version_id": "24.04",
    "lts": true
  },
  "build_metadata": {
    "path": "serverseed_0.1.0_build.json",
    "sha256": "hex"
  },
  "artifacts": [
    {
      "name": "serverseed",
      "type": "binary",
      "architecture": "amd64",
      "target": "x86_64-unknown-linux-gnu",
      "path": "serverseed_0.1.0_linux_amd64",
      "sha256": "hex",
      "size": 123456,
      "runtime_dependencies": ["libc.so.6", "ld-linux-x86-64.so.2"],
      "compatible_config_revision": {"min": 1, "max": 1},
      "compatible_migration_revision": {"min": 0, "max": 0}
    }
  ]
}
```

`target_profiles`は適用可能な構成の配列とし、`server`または`mining`を指定する。共通基盤の成果物は両構成を指定できる。構成固有の成果物は対象構成のみを指定し、異なる構成の成果物を混在させない。保存済み構成が配列に含まれない、または対象構成を検証できない場合は適用しない。旧マニフェストの移行は明示的に定義し、欠損時に対象を推測しない。

`artifacts`には配布する各アーキテクチャの本体を一件ずつ記載する。上の例は一件を抜粋した形式例であり、`hex`とサイズは実配布値へ置き換える。`type`は`binary`、`architecture`と`target`の対応は[ビルドターゲット](ci-cd.md#配布バイナリのターゲットとリンク)に従う。未対応CPU、重複候補、欠損フィールド、未知の型、サイズ・ハッシュの不一致を拒否する。

`path`は配布基点からの相対ファイル名とし、`[A-Za-z0-9][A-Za-z0-9._-]*`に一致する値だけを受け入れる。絶対パス、URL、親ディレクトリ参照、区切り文字、制御文字を含めない。`size`は正の整数バイト数、実配布の`sha256`は64桁の小文字16進数とする。`runtime_dependencies`は必要な共有ライブラリとローダーを列挙する。ABIの詳細は[ビルドメタデータ](ci-cd.md#本体ビルドメタデータ)で固定し、`build_metadata`のハッシュで検証した後に導入先と照合する。この参照が欠ける場合も停止する。

互換範囲は整数の`min`以上`max`以下を表し、`min > max`は不正とする。構成未選択では現在の構成リビジョンを推測せず、OS・CPU・実行時依存と共通基盤への適用条件だけを検査する。本体の自己申告との照合は[version](cli.md#version)を使用する。

本体マニフェストはISOへ収録するため、ISO自身のハッシュを含めない。ISOのハッシュと収録本体との対応は[媒体マニフェスト](usb.md#媒体マニフェスト)に置き、循環参照を作らない。

マニフェストに未対応の`schema_version`、Ubuntu 24.04 LTS以外の対象バージョン、現在状態から移行不能なリビジョンが含まれる場合は更新しない。初期実装は本体用の版`2`だけを受け入れ、旧deb形式を自動変換しない。
