# CI/CDとリリース仕様

[文書一覧](../DOCUMENT_INDEX.md)

## CI/CD

実行基盤と責任分担は[CI/CD](../PRINCIPLES.md#cicd)、リポジトリ運用は[AGENTS.md](../../AGENTS.md)を参照する。

実行の許可条件は[CIとリリースの実行許可](../POLICIES.md#ciとリリースの実行許可)を参照する。

workflowごとの処理は次の定義に従う。

初期workflowは次とする。

| workflow | トリガー | 目的 |
|---|---|---|
| `ci.yml` | pull request、`main`へのpush | 通常CI |
| `release.yml` | `v*`タグ、手動実行 | リリース成果物作成 |
| `vm-test.yml` | 手動実行のみ | VMを使う破壊的操作の検証 |

通常CIとVM試験の適用条件は[CIの隔離](../POLICIES.md#ciの隔離)を参照する。

正式公開の検証条件は[公開前の検証](../POLICIES.md#公開前の検証)を参照する。

初期CIで必須とするジョブは次のとおりとする。

| ジョブ | 内容 |
|---|---|
| `format` | `cargo fmt --all -- --check`およびMarkdown整形確認 |
| `lint` | `cargo clippy --all-targets --locked -- -D warnings`、危険な外部コマンド実行と[依存関係](#依存関係の検査)の検査 |
| `test-unit` | `cargo test --lib --locked`によるunit test |
| `test-integration` | `cargo test --tests --locked`によるUbuntu 24.04 LTS上のCLI契約と、使い捨てコンテナ内での本体管理の検査 |
| `build` | `cargo build --release --locked --target TARGET`による`serverseed`バイナリ作成。`TARGET`は[配布ターゲット](#配布バイナリのターゲットとリンク)に従う |
| `package-iso` | 検証済みビルド成果物を使うUSB用ISOの作成と内容検査 |
| `spec-check` | [仕様充足](#仕様充足の検査)、[文書索引の製品仕様](../DOCUMENT_INDEX.md#製品仕様)と実装上の固定値の矛盾、[受入条件とテストの対応](#仕様とテストの対応)の検査 |
| `cli-contract` | サブコマンド、共通オプション、JSON出力契約の検査 |

実行環境での禁止操作は[CIの隔離](../POLICIES.md#ciの隔離)を参照する。

ServerSeedのCIは、GitHub workflowから少なくとも次のローカルスクリプトを呼び出せるようにする。

```bash
ci/run-format
ci/run-lint
ci/run-unit
ci/run-integration
ci/run-build
ci/run-package
ci/run-spec-check
ci/run-cli-contract
ci/run-all
```

各CIコマンドはローカル開発環境でも実行できるようにし、workflowから共通利用する。

### GitHubの役割

基盤の適用範囲は[現行の運用基盤](../POLICIES.md#現行の運用基盤)に従う。本書で定義するGitHubのCI/CD上の役割は次のとおりとする。報告の受付条件は[報告ポリシー](../POLICIES.md#報告の受付)を参照する。

- CI/CD workflowの起動
- CI結果の表示
- リリースタグ管理
- [配布先](../PRINCIPLES.md#成果物の配布)へのリリース成果物と検証情報の公開

GitHub Actionsを使用する場合、workflowは`.github/workflows/`に配置する。重複を避けるため、必要に応じて`ci/`および`release/`配下の補助スクリプトを呼び出す。

将来の基盤へ移行する場合は、[移行条件](../POLICIES.md#運用基盤の移行条件)に従ってworkflow・スクリプトと成果物の対応を見直す。本節は切替済みであることを示さない。

### CI実行環境

標準環境は[CI実行基盤](../PRINCIPLES.md#ci実行基盤)を参照する。

CI実行環境には、[Rustツールチェーン方針](../PRINCIPLES.md#rustツールチェーン)に従うコンパイラー・Cargo・rustfmt・Clippy、[ISO生成](usb.md#isoの作成)のツールおよび署名検証ツールを事前に導入する。ビルドターゲットに必要な標準ライブラリ、リンカーおよびシステムライブラリもCI用イメージに含める。

環境変更の条件は[CI環境の変更](../POLICIES.md#ci環境の変更)に従う。

イメージ定義の管理は[CI実行基盤](../PRINCIPLES.md#ci実行基盤)を参照する。

## 仕様充足の検査

`spec-check`は、文書索引、対象機能と使用する共通契約のファイル・節、[完全仕様の必須条件](../POLICIES.md#完全仕様の必須条件)との対応、受入検証の設計、実装変更がある場合は変更ファイルとテストの対応を入力とする。

1. 全文書の相対リンク・節アンカーと文書索引の網羅性を確認し、同じ定義の重複・参照切れを検出する。
2. 対象範囲の各確認項目を正本へ対応付け、欠落、未確定、矛盾、理由のない適用外、例示だけの定義を抽出する。曖昧な表現は文脈と参照先を含めて確認し、単語の有無だけで充足と判定しない。
3. 対象外とした未確定事項への依存がないことを確認し、[実装着手と仕様充足の判定](../POLICIES.md#実装着手と仕様充足の判定)に照合する。依存する例外は[依存関係の検査](#依存関係の検査)へ対応付ける。
4. 受入条件ごとの前提・入力・期待結果と検証方法を確認する。実装変更がある場合は[仕様とテストの対応](#仕様とテストの対応)で実装・テストの漏れを検査する。
5. 結果には対象コミットと対象範囲、正本のファイル・節、確認項目、充足・未達・適用外の判定と根拠、承認対象との対応を含める。

自動検査だけで判断できない項目は確認待ちとして残し、根拠のない成功にしない。実装対象の未達・確認待ちは検査失敗とする。文書だけの変更では未達事項を明示できるが、実装着手可能の判定には転用しない。

検査自体の受入条件は、必要項目が揃う対象の成功、項目欠落・不正な適用外・切れた参照・矛盾・未確定依存・期待結果やテストの欠落の検出とする。未達事項を含む文書変更の成功と、未達対象の実装変更の失敗を区別できることも確認する。検査の実装状況は[ロードマップ](../ROADMAP.md)を参照する。

## 依存関係の検査

`lint`では[憲章第7条](../CHARTER.md#第7条-提供元依存権利)と[依存条件](../POLICIES.md#rustと内製crateの依存条件)への適合を、次の入力と判定で検査する。変更時の実施手順は[作業ルール](../../AGENTS.md#rustと内製crateの依存制約)を参照する。

1. ルートと全内製crateのCargo manifestを構造化して読み、通常・開発・ビルド・workspace・ターゲット別・任意・条件付きの全依存宣言を列挙する。featureの既定値や現在のホストで有効な依存だけに絞らない。
2. 各path依存を正規化し、シンボリックリンク解決後もリポジトリ内にあることを確認する。registry・Git参照、第三者コードの持込み、リポジトリ外の実体を検出する。ローカルパスや`source: null`だけを内製の証明にしない。
3. `Cargo.lock`と`cargo metadata --format-version 1 --locked`の構造を照合し、依存グラフ、版、manifestの実体、所有責務を確認する。無効化済み・他CPU向けの宣言は手順1でも検査し、metadataの有効グラフだけで判定しない。lockfileに残った禁止依存も検出する。
4. `build.rs`、マクロ、生成コード、リンカー指定、FFI、vendor資材およびダウンロード処理を確認し、manifest外から禁止依存が入らないことを検査する。許可された[OS実行時依存](#配布バイナリのターゲットとリンク)と任意のアプリケーションライブラリを区別する。
5. 外部プログラム・Action・CIイメージ・ISO資材を[例外台帳](../DEPENDENCY_EXCEPTIONS.md)のIDと対応付け、対象・現在状態・個別採用情報を[例外の使用条件](../POLICIES.md#外部依存例外の使用条件)へ照合する。対象の漏れ、ID重複、未確定項目のある使用可能判定、承認用途・固定参照・ライセンス・ハッシュ・署名・検証結果との不一致を検出する。

不一致・未選定・未確認は検査失敗として、対象宣言または資材、正本の制約、停止理由を報告する。自動削除、依存の自動追加、lockfileの自動更新で合わせない。結果はビルド元コミットと検査環境へ紐づけ、リリース工程でも同じ対象を検査する。未実装の検査を合格扱いにしない。

## テスト体系

テストは次の階層で実施する。

| 種別 | 対象 |
|---|---|
| unit | 状態判定、設定読み込み、マニフェスト検証、更新計画 |
| integration | Ubuntu 24.04 LTSコンテナ上でのCLI、隔離した使い捨て環境での本体導入・更新・削除、読み取り専用検査 |
| vm | ディスク、ブート、復旧、破壊的操作を含む検証 |
| fixture | `/etc/os-release`、lsblk、systemctlなどの実行結果サンプル |

unit testは対象モジュール内の`#[cfg(test)]`で定義し、integration testの入口は`tests/*.rs`に配置する。fixtureは`tests/fixtures/`に保存する。実行コマンドは[CIジョブ](#cicd)に従う。

構成選択に既定値がないこと、`--yes`・cloud-initが初回選択を代行しないこと、保存構成の継承、不整合時の停止、[選択構成に対応する機能](../POLICIES.md#構成の分離)だけを適用することをunit・integrationで検証する。マイニングの採掘停止、通信断、温度異常および更新失敗はfixture・模擬サービスで検証し、実採掘の制約は[検証環境の制約](../POLICIES.md#検証環境の制約)に従う。GPU・BIOS・復電起動は別の実機検証として結果を記録する。

テスト階層の適用条件と危険操作の隔離は[検証環境の制約](../POLICIES.md#検証環境の制約)に従う。

### 状態判定と非変更操作の受入条件

下表の前提と検証対象をunit・integrationのケースへ対応付ける。期待する判定・副作用・停止条件は参照先の正本から照合し、表内で別定義しない。USB固有の状態はfixtureまたはテスト用ディスクイメージで再現し、危険操作は[検証環境の制約](../POLICIES.md#検証環境の制約)に従って隔離する。

| 前提・入力 | 正本と確認対象 |
|---|---|
| 外部媒体・SSH実行環境から検査する空ディスク、構成未セットアップの対応OS、本体だけ導入済み・正常削除済みのOS | [判定順序](common-platform.md#状態判定の優先順位)と[本体導入情報](common-platform.md#本体導入と構成管理)。初回の未作成と導入・管理の不整合を区別できること |
| 整合する管理情報、管理ファイル欠損・破損、構成不一致、中断した導入・変更 | [管理マーカー](common-platform.md#管理マーカー)と[前回処理状態](common-platform.md#前回処理状態)を判定順序へ照合できること |
| 管理マーカーが残る未対応OS、OS情報欠損・読み取り不能、対象ディスク読み取り不能 | [対応OSの判定](product-scope.md#ubuntu-2404-lts判定)を含む判定順序の優先関係を確認できること |
| 読み取り専用コマンド、`plan`、`--dry-run`で中断を検出、管理ディレクトリ・ロック未作成 | [読み取り専用時の記録処理](common-platform.md#読み取り専用時の記録処理)に従う判定・出力と、実行前後のファイル・ディレクトリ・既定ログの不変を確認できること。成果物保存の有無は[保存条件](../POLICIES.md#成果物の保存)に照合する |
| ログ保存先の権限不足・読み取り専用属性・メタデータ取得不能、親操作内のトランザクション診断 | [doctor](cli.md#doctor)の診断根拠・未確認表示、試験書き込みの不在、親の操作記録の不変を確認できること |
| ローカル・HTTPSからの本体導入・更新の計画と実行、候補未取得、署名・メタデータ・本体ハッシュの不一致 | [計画時と実行時の検証](lifecycle.md#計画時と実行時の検証)の検査範囲、未実施の表示、取得・起動・保存の有無、適用前の検証と差異発生時の再確認を区別できること |

ケースと結果の追跡は[仕様とテストの対応](#仕様とテストの対応)に従う。本節は受入条件の定義であり、実装・試験が完了したことを示さない。

### 仕様とテストの対応

[仕様駆動型開発](../../AGENTS.md#仕様駆動型開発)の追跡は、各テストケースと検査結果から、正本の相対パス・節アンカー、対象の受入条件、正常・異常・境界値の区分、ケース名を特定できる形式とする。仕様値は正本への参照を使い、テスト用の別仕様書へ複製しない。

`spec-check`の確認手順は[仕様充足の検査](#仕様充足の検査)に従う。対応には承認対象の仕様版・コミット、実装のファイル・識別子、テストケースと検査結果の所在も含め、仕様だけが存在する状態と実装・検証済みの状態を区別する。内製crateの差し替えでは同じ契約テストを新旧双方へ適用し、差異と未検証条件を報告する。依存制約は[依存関係の検査](#依存関係の検査)、外部操作の隔離は[検証環境の制約](../POLICIES.md#検証環境の制約)を参照する。

### 配布・導入の受入条件

| 対象 | 必須の検証 |
|---|---|
| 内製依存・例外 | 禁止依存の直接・推移・任意・別CPU宣言、リポジトリ外path、持込み・リンクによる迂回、未承認・版未固定の外部資材を検出して停止できること |
| crate差し替え | 同じ契約テストで正常・異常・境界値を照合し、CLI・設定・保存形式・失敗時動作の互換範囲と未達条件を確認できること |
| 初回導入 | 対応OS・CPUへの配置、構成未選択の維持、依存不足・権限不足・容量不足時の停止 |
| 再導入・削除 | 同一版の冪等性、所有元不明・deb所有ファイルとの競合停止、設定保持、利用中本体の削除拒否 |
| 取得・検証 | 通信断、TLS不正、署名不正、失効鍵、ハッシュ不一致、異なるCPU、旧版への巻き戻しの拒否 |
| 本体更新・復旧 | ロック競合、配置直前・直後の中断、診断失敗、旧版復元、復旧不能時の停止と記録 |
| USB用ISO | [ISOの作成](usb.md#isoの作成)に従うバイナリ一致、USB・仮想メディア起動、外部通信なしでの本体起動。[内蔵OSの起動確認](firmware.md#内蔵osの起動確認)を媒体を外して実施 |
| VPS | [Cloud導入](cloud.md)のSSH実行環境と対象OSの識別、空ディスクへのOS導入と既存OSへの構成適用、起動・再接続。操作選択は[マスターのフロー](../master/specification.md#自動処理の流れ)へ照合 |

正常系・異常系とも、成功・停止・失敗の終了コードとJSON出力を[CLI契約](cli.md#共通json出力)に照合する。シンボリックリンクと一般ユーザーによる入力差し替えも検査する。試験対象の保護条件は[検証環境の制約](../POLICIES.md#検証環境の制約)を参照する。

### 自動化と通常運用の受入条件

下表は追加した導入・保守方式の検証対象と正本の対応とする。具体的なCLI・形式・時間制限などが未確定の対象は、契約確定後にケースを具体化する。現在は試験コード・環境とも未作成であり、実行済みの結果ではない。

| 前提・入力 | 正本と確認対象 |
|---|---|
| 物理PCの導入・保守完了後、起動媒体を取り外して起動・再起動 | [内蔵OSの起動確認](firmware.md#内蔵osの起動確認)。通常サービスの媒体への依存の有無を検査し、マスターは[構成の検証](../master/specification.md#構成の検証)へ照合 |
| 初期の物理マスター構築、内蔵OSからのCloud管理、マスターの未設定 | [初期構築](../master/specification.md#初期構築)と[運用条件](../POLICIES.md#実行入口と通常運用)。選択構成・実行入口と機能の準備状態を照合 |
| 操作・対象・初回構成・保存先の未選択、対話不能、`--yes`・設定による代行、確認後の対象変化 | [必須選択と自動実行](../POLICIES.md#必須選択と自動実行)、[更新計画](lifecycle.md#更新計画)。対象側の追加手入力ではなく、入口側の確認を検査 |
| SSH接続可能だがOS未導入、権限・コマンド不足、実行環境と対象OSが異なる、実行中ディスクとの混同 | [Cloudの能力検査](cloud.md#実行環境と対象os)、[状態判定](common-platform.md#状態判定の優先順位)と[ディスク操作](../POLICIES.md#ディスク操作)。接続成立・対象状態・適用可否を別に照合 |
| SSH切断、対象再起動、マスター停止、応答欠損、ホスト鍵変更、重複要求 | [中断と結果照合](../master/specification.md#中断と結果照合)と[実行側と対象側](lifecycle.md#実行側と対象側)。未確認表示、照合、再投入の制御を検査 |
| 外部媒体・Cloudでの独立バックアップと更新内バックアップ、保存先未指定・容量不足・破損 | [バックアップ](backups.md#実行と保存先)と[データ保護](../POLICIES.md#バックアップとデータ保護)。対象・保存先と結果、更新続行可否を照合 |
| 媒体なしの採掘起動・運転障害復旧、timerやOS自動更新による独立した適用要求 | [通常運用](../POLICIES.md#実行入口と通常運用)、[共通timer](../POLICIES.md#共通timer)、[自動更新](../POLICIES.md#マイニングの自動更新と再起動)。運転と導入・保守の区別を検査 |

SSH・OS導入・再起動・復元の試験は、模擬接続先または隔離したテスト用VMとディスクで行い、[CIの隔離](../POLICIES.md#ciの隔離)を適用する。文書検査の成功をこの表の動作試験の成功に読み替えない。

|---|---|
| 初回に三つの構成をそれぞれ選択、未選択・対話不能・自動代行の入力 | [構成選択](../POLICIES.md#構成選択と継続管理)と[構成値の型](configuration.md#configyml)。選択成立・停止と保存対象を照合 |
| 単独構成とマスター構成の機能適用、Cloudからの構成選択、機器が一部機能に非対応 | [構成選択](../POLICIES.md#構成選択と継続管理)、[Cloudの前提](cloud.md#前提)、[機能適用の範囲](../POLICIES.md#構成の分離)と[マスターの対応範囲](../master/specification.md#対応範囲)。選択と適用可否を区別し、導入対象、非対応時の停止と別構成への置き換えの有無を確認 |

| マスター固有データのバックアップ・復元とマスター喪失時の復旧 | [管理情報の保全と復元](../master/specification.md#管理情報の保全と復元)と[共通バックアップ契約](backups.md#未確定契約)。固有の保全範囲と共通手段を分離し、未確定事項を照合 |
| 旧二択形式、更新情報にマスターの宣言がない場合、異なる構成の成果物 | [構成記録の互換性](configuration.md#構成記録の互換性)と[更新マニフェスト](lifecycle.md#更新マニフェスト)。互換性・適用対象と未確定部分の停止を照合 |
| 内包機能の適用・検証失敗または未確認、途中中断、再実行・更新・復旧 | [構成の検証](../master/specification.md#構成の検証)と[状態判定](common-platform.md#状態判定の優先順位)。一部機能の結果と構成全体の完了判定を照合 |
| 採掘側だけが再起動を許可、機能別ポリシーの衝突、SSH管理操作の実行中・結果未確認 | [マスター管理構成の運用](../POLICIES.md#マスター管理構成の運用)。ホスト変更の許可条件・計画確認・停止と管理記録の保全を照合 |

CLI・移行・同居制御など未確定の契約に依存するケースは、その確定後に具体化する。現在は受入対象の対応付けであり、実装・試験が完了したことを示さない。機能間の資源配分や時間制限を、試験作成時に独断で補完しない。

## リリース

リリースはGit tagで管理する。タグ形式は`vMAJOR.MINOR.PATCH`とする。

管理者がリリース操作を実行した場合、CDは次を生成する。

- Linux amd64用`serverseed`バイナリ
- Linux arm64用`serverseed`バイナリ
- USB起動用amd64 ISO
- USB起動用arm64 ISO
- 本体用と媒体用のマニフェスト
- 本体ビルドメタデータ
- SHA-256チェックサム
- OpenPGP detached signature

公開対象の選定は[公開前の検証](../POLICIES.md#公開前の検証)に従う。

リリース成果物名は次を基本とする。

```text
serverseed_VERSION_linux_amd64
serverseed_VERSION_linux_arm64
serverseed_VERSION_usb_amd64.iso
serverseed_VERSION_usb_arm64.iso
serverseed_VERSION_build.json
serverseed_VERSION_manifest.json
serverseed_VERSION_manifest.json.asc
serverseed_VERSION_media.json
serverseed_VERSION_media.json.asc
serverseed_VERSION_checksums.txt
serverseed_VERSION_checksums.txt.asc
```

`VERSION`はGit tagの先頭`v`を除いたSemantic Versioning値とする。例として、タグ`v0.1.0`の場合は`serverseed_0.1.0_linux_amd64`とする。

リリース操作は、少なくとも次のコマンドで実行できるようにする。

```bash
release/build
release/build-iso
release/sign
release/verify
release/publish
```

`release/publish`の許可条件も[公開前の検証](../POLICIES.md#公開前の検証)に従う。

### リリース工程

1. 固定タグ・コミットから両アーキテクチャの本体を一度だけビルドし、[受入条件](#配布導入の受入条件)を検証する。
2. 本体のビルドメタデータと[更新マニフェスト](lifecycle.md#更新マニフェスト)を確定し、本番鍵でマニフェストへ署名する。これ以降、本体・メタデータ・マニフェストを変更しない。
3. `release/build-iso`に固定版の本体と署名付き情報を渡す。既存リリースから取得する場合も同じ検証を行う。ISO内のバイナリと候補バイナリをハッシュで照合し、別ビルドに置き換えない。
4. [ISOの作成](usb.md#isoの作成)と手動VM試験を完了し、生成したISOの情報を[媒体マニフェスト](usb.md#媒体マニフェスト)に記載して署名する。
5. 全配布ファイルのSHA-256一覧を作成し、一覧にも署名する。一覧自身とその署名は一覧の対象外とする。`release/verify`で相互参照とすべての必要な成果物を検査する。
6. 検証済み一式を非公開のdraft releaseへ配置し、取得後の再照合に成功した場合のみ同一タグの正式リリースとして公開する。部分失敗、成果物不足、ハッシュ変更がある場合は公開しない。

公開後の扱いは[公開物の固定](../POLICIES.md#公開物の固定)を参照する。

### 署名鍵の扱い

鍵の分離・保管・利用は[リリース署名鍵](../POLICIES.md#リリース署名鍵)を参照する。

### アーティファクト検査

本体の導入・更新・削除は、少なくとも次を検査する。

- [配置と権限](lifecycle.md#初回の取得と配置)が正しく、設定・状態・ログが保護されること
- 構成未選択のまま本体だけを導入でき、`doctor --json`がその状態を区別すること
- 再導入、署名不正、競合配置、中断および復旧を[受入条件](#配布導入の受入条件)どおり扱うこと

生成したバイナリは、少なくとも次を検査する。

- `serverseed version`が成功すること
- `serverseed inspect --json`がJSONのみを標準出力へ出すこと
- `serverseed --help`が成功すること
- `serverseed doctor --json`がJSONのみを標準出力へ出すこと
- `serverseed plan update --json`が変更なしで計画またはブロック理由を出すこと

実行環境と実行時依存の検証は[配布バイナリのターゲットとリンク](#配布バイナリのターゲットとリンク)に従う。新しいUbuntu環境で、RustやCargoを導入せず配布本体を実行できることも確認する。

ISOは[媒体マニフェスト](usb.md#媒体マニフェスト)の収録版・ハッシュと[起動互換性](firmware.md#isoの起動互換性)を検査する。生成成功だけで合格にせず、構成選択前の非破壊性とUSB・仮想メディア双方の起動を確認する。

### 本体ビルドメタデータ

`serverseed_VERSION_build.json`は次の形式とする。値は形式例であり、実際の採用版・ビルド結果へ置き換える。

```json
{
  "schema_version": 1,
  "serverseed_version": "0.1.0",
  "tag": "v0.1.0",
  "commit": "commit-sha",
  "built_at": "RFC3339",
  "rustc_version": "adopted-version",
  "cargo_version": "adopted-version",
  "cargo_lock_sha256": "hex",
  "artifacts": [
    {
      "architecture": "amd64",
      "target": "x86_64-unknown-linux-gnu",
      "build_environment": "image-digest",
      "link_mode": "dynamic",
      "elf_interpreter": "/lib64/ld-linux-x86-64.so.2",
      "libraries": [
        {"soname": "libc.so.6", "required_versions": ["GLIBC_2.39"]}
      ],
      "linked_crates": []
    }
  ]
}
```

アーキテクチャごとに一件を記載し、版・タグ・コミットを本体用マニフェストとビルド対象へ照合する。`link_mode`は`static`または`dynamic`、静的リンク時の`elf_interpreter`は`null`とする。`libraries`は実際のELF依存と要求するABIの集合を記録し、`linked_crates`は組み込んだcrate名・バージョンを持つオブジェクトの配列とする。依存を推測で省略しない。標準ライブラリは上位のツールチェーン情報で、内製crateは`linked_crates`で識別し、[依存条件](../POLICIES.md#rustと内製crateの依存条件)と[例外一覧](../DEPENDENCY_EXCEPTIONS.md#外部依存の例外一覧)への適合を確認する。

導入時は必要なローダー・ライブラリ・要求ABIをすべて照合する。条件を判定できない場合は実行可能と扱わない。本体用マニフェストの署名と、このファイルへのSHA-256参照で真正性を確認し、未検証のメタデータで依存確認を省略しない。
